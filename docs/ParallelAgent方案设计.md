# ParallelAgent 方案设计

> 最后更新：2026-10-15

## 1. 背景与问题

### 1.1 已验证的旧模式

ColorWars 项目实战过"仲裁者 + 四轨（T-A/B/C/D）独立会话"的多 AI 并行开发：

- **单一事实来源三层**：契约块（结论，嵌代码注释）+ 仲裁文档（推理全文）+ 交接手册（冷启动入口）；
- **文档即消息**：仲裁者写"转达单"（按轨分节），各轨写回执（引用裁决编号 + 证据）；
- 每批节奏：写单 → 派发 → 各轨并行 → 回执 → 仲裁者独立实检 → 下一批。

该模式的优点（必须保留）：**全程文件留痕、可溯源、抗会话死亡与上下文压缩**；裁决编号稳定、纪律密度高。

### 1.2 唯一的结构性痛点：人肉邮差

旧环境的会话间直发通道（peer SendMessage）不稳定——会话会离线、需授权、要登记身份，一断就退化为**用户复制转达单段落、人肉转发给各轨**。由此带来：

- 用户成为系统的消息总线，并行轨道越多损耗越大；
- 快照漂移（写单与发单之间代码又动了）、发错轨、空转达（待命轨无活）等运维税。

### 1.3 本项目目标

**保留文件可溯源体系，消灭人肉转发环节**：仲裁者会话通过一个自动化编排层，自行完成对多个常驻 Trae Work 任务会话的"建会话、派活、收工判定"，用户只在产品口径决策与异常升级时介入。

非目标（明确不做）：

- 不用 UI 自动化传递工作内容（裁决/代码/证据一律走文件）；
- 不做跨机分布式、不做多用户；
- 不追求 7×24 无人值守，一期只覆盖"用户在场的并行开发批次"。

## 2. 环境事实（已实测，2026-10-15）

| 项 | 事实 | 证据 |
|---|---|---|
| 安装形态 | 机器上只有一个 Trae：`D:\Programs\Trae\Trae CN.exe`，**Work 与 IDE 是同一二进制的两个"场景"**，不是独立程序 | 进程枚举、安装目录扫描 |
| 版本 | Trae CN 1.107.1（stable），Electron 内核 Chromium 142 | `resources/app/product.json`；CDP 探测返回 `Chrome/142.0.7444.235` |
| Work 界面技术栈 | 本地 workbench 的 solo-lite 裁剪变体（**本地 renderer，非远程网页、非独立 webview**） | `out/vs/code/electron-browser/scenes/desktop.config.js`、`workbench.desktop.main.solo-lite*.js` |
| CDP 调试端口 | 启动加 `--remote-debugging-port=<port>` 后端口开放，`/json/version`、`/json` 目标枚举均正常（用临时 user-data-dir 实测，未动主实例） | 当日 CDP 探针 |
| 扩展能力 | Work 场景共用 VS Code 扩展宿主（左侧有"插件市场"），理论上可装本地扩展 | 目录结构 + 产品形态 |
| 多任务 | 同一项目可创建多个独立任务会话（左侧任务面板），各自独立上下文、共享同一文件系统；**任务之间无官方会话间消息通道** | 官方文档《多任务并行》 |
| 会话创建权 | 新建任务的官方入口只有用户侧 UI/快捷键；Agent 自身没有"创建持久会话"的 API | 官方文档 + 现有工具集确认 |

**推论**：自动化必须从应用**外层**（CDP）或**扩展宿主层**（插件）接入，不存在官方编排 API。

## 3. 总体架构（与最终方案无关的固定部分）

### 3.1 数据面 / 控制面分离（核心设计原则）

```
┌─────────────────────── 数据面（100% 文件，可溯源）──────────────────────┐
│  契约块（嵌代码） │ 转达/第N轮.md │ 回执/T-X-第N轮.md │ 快照.md │ 手册  │
└──────────────────────────────────────────────────────────────────────┘
              ▲ 仲裁者用原生文件工具直接读                    ▲ 各轨自己读写
              │                                              │
┌─────────────┴──────────────┐                ┌──────────────┴──────────────┐
│  仲裁者会话（主控）          │                │  轨道会话 T-A/B/C/D（常驻）   │
│  - 写转达、读回执、独立实检    │                │  - 读自己的转达节、干活、写回执  │
│  - 调用编排器（只传控制信号）  │               │                              │
└─────────────┬──────────────┘                └──────────────▲──────────────┘
              │  控制面（只有控制信号，不含工作内容）             │
              │  new / dispatch / watch / ping                │
              ▼                                               │
        ┌────────────────────────────────────────────────────┐
        │  编排器（候选实现：CDP-DOM 方案 或 插件方案，见 §4/§5） │
        │  操作 Work 窗口：建任务、切轨、粘贴固定话术、发送、       │
        │  判定空闲/弹窗                                       │
        └────────────────────────────────────────────────────┘
```

**铁律：自动化通道只传"摇铃"信号，消息体是固定话术 + 文件路径指针，绝不含裁决内容。** 这样即使控制层出任何故障（误点、误读），最坏结果只是"铃没摇成"，不会把错误内容送进错误的轨。

### 3.2 文件信箱约定（沿用 ColorWars 并升级）

```
docs/协调/
  轨道启动手册.md            # 新会话首条消息永远指向它："读手册，你是 T-X，待命"
  转达/第N轮.md              # 仲裁者只写一次，按轨分节（不再复制转发）
  回执/T-X-第N轮.md          # 各轨收工自写：引用裁决编号 + 证据形式 + 完成时点
  快照.md                    # 仲裁者每批后回写：轨/状态/欠账
```

回执文件的**出现与 mtime 即完成信号**——编排器轮询文件系统即可，原则上不需要从 UI 读取各轨输出。

### 3.3 一轮批次时序

1. 仲裁者写 `转达/第N轮.md`（写前当场核验关键文件现状，防快照漂移）；
2. 编排器对各活跃轨执行 `dispatch`：切到目标任务 → **身份核对**（当前任务名 = T-X）→ 粘贴固定话术（"读转达第 N 轮你的 →T-X 节，执行，写回执"）→ 发送；
3. 各轨并行常驻执行；编排器 `watch`：轮询回执目录，辅以 UI 状态检测（卡死/弹窗）；
4. 回执到齐（或超时）→ 仲裁者读回执、**独立实检、不采信转述** → 更新契约块/快照 → 下一批；
5. 连续两批活跃轨 <2 → 按既有收缩判据回归单线。

### 3.4 开启条件（沿用，不为用机制而开轨）

契约已冻结、≥2 条文件边界正交的真活轨道、串行等待确成瓶颈——三条全满足才开。

## 4. 候选方案 A：CDP / DOM 注入

### 4.1 原理

带 `--remote-debugging-port=<非默认端口>` 启动 Trae 后，编排器（本机 Python 脚本，CDP 客户端走 WebSocket）连接 Work 窗口的 renderer target：

- `Target.getTargets` 找 Work 场景页面；
- `Runtime.evaluate` 执行 JS：查 DOM、定位任务卡片/输入框/发送按钮、读状态；
- `Input.dispatchKeyEvent` / 原生 setter + `input` 事件 + 剪贴板粘贴写入文本；
- 注入 `MutationObserver` 常驻脚本：监听任务列表变化、发送/停止按钮状态切换（空闲判定）、弹窗出现。

### 4.2 能力清单

| 编排动作 | 实现方式 |
|---|---|
| 列出任务会话 | 读左侧任务卡片 DOM，OCR 不需要（innerText 直接可得） |
| 新建任务 | 快捷键（Ctrl+Alt+N）或点"新建任务"入口 |
| 切换轨道 | 点击任务卡片 |
| 派活 | 聚焦输入框 → 剪贴板粘贴固定话术 → 发送 |
| 身份核对（防发错轨） | 发送前读当前激活卡片标题，断言 = 目标轨 |
| 空闲/完成判定 | 回执文件为主；按钮状态（发送⇄停止）DOM 观察为辅 |
| 异常诊断 | 弹窗/报错 DOM 检测；必要时截图留存 |

### 4.3 优点

- 无坐标、无图像识别、**不抢焦点、后台窗口可操作**、中文文本零误读、毫秒级；
- 能直接读 DOM 状态，空闲检测从"猜屏幕"变为"读状态"；
- 编排器独立于 Trae 进程，开发调试简单（改脚本不用重启 IDE）。

### 4.4 缺点与风险

- **DOM 选择器是 Trae 私有实现**，版本更新可能变；缓解：只用稳定锚点（role/aria/文本/placeholder），配 fail-stop（找不到预期元素即停机告警，禁止盲点），选择器外置配置；
- 使用时需**带端口重启一次 Trae**（Chromium 不能热附加，单实例锁）；
- **端口安全**：调试端口对本机所有进程开放 = 完整操控 IDE。必须绑 127.0.0.1、用非默认端口、编排器不工作时不带参数启动；
- 官方更新理论上可移除调试开关（当前未封）；
- **自指风险**：目标窗口与仲裁者同属一个 Trae，注入逻辑出错时可能操作仲裁者自己的会话——身份核对断言是硬门禁。

## 5. 候选方案 B：本地扩展（插件）

### 5.1 原理

开发一个只含本地能力的 VS Code 风格扩展，装入 Trae 扩展宿主：

- 扩展激活后起**本地 HTTP/文件监听服务**，对仲裁者会话而言相当于一个"会话管理 API"；
- 用 `commands.getCommands(true)` dump 全部内部命令，寻找 Work/solo 场景注册的任务类命令（新建任务、切换任务、打开任务、发消息等）；
- 若命令存在：一切操作走命令调用，**完全不碰 DOM**；
- 文件信箱轮询、会话身份表、弹窗告警等逻辑天然在 Node 侧完成。

### 5.2 优点

- 最抗 UI 改版：命令 API 比 DOM 稳定一个量级；
- 无需调试端口、无重启注入、无端口暴露面；
- 与 IDE 同生命周期、同权限，能访问 workspace、窗口、命令系统。

### 5.3 缺点与风险（决定性的未知数）

- **扩展宿主无权操作 workbench DOM，也没有官方"向某个任务会话发消息"的 API**——是否存在可复用的内部命令**完全取决于 Trae 自己注册了什么**，需实测；
- 若关键动作（尤其"向指定任务输入并发送消息"）没有命令，插件无法独立闭环，只能退为方案 A 的配套（承担 HTTP 网关/文件监听/命令触发，DOM 动作仍走 CDP）；
- 扩展与 Trae 版本耦合，更新后内部命令可能变更或消失；
- 分发/加载方式需确认（本地 vsx 直装是否被 Work 场景接受，待实测）。

### 5.4 可能的终态：A+B 组合

- **插件**：本地 HTTP 网关、文件信箱 watch、能命中的内部命令（新建/切换任务）、身份表持久化；
- **CDP**：仅插件命令覆盖不到的动作（输入框写入/发送/状态观察）。
- 组合方案减少 CDP 触点，但引入两个部件的维护成本——只有在实测表明命令覆盖率高时才值得。

## 6. 两案对比与决策判据

| 维度 | A：CDP/DOM | B：扩展插件 |
|---|---|---|
| 闭环能力（预期） | 高，DOM 全部可操作 | 取决于内部命令是否存在，**不确定** |
| 抗 UI 改版 | 中（稳定锚点 + fail-stop 缓解） | 高（若命令存在） |
| 安全面 | 调试端口暴露（可管控） | 无额外端口 |
| 启动成本 | 需带参数重启 | 装扩展一次 |
| 开发调试 | 独立脚本，迭代快 | 改扩展需重载宿主 |
| 被官方更新封死的可能 | 低（CDP 是 Chromium 标配） | 中（内部命令非公开契约） |

**决策方式**：不预判，重启 Trae 后按 §7 探针实测，用结果投票：

1. 插件命令 dump 若覆盖"新建/切换/发送消息"全链路 → 选 B（或 B 为主）；
2. 仅覆盖部分 → A+B 组合；
3. 关键命令不存在 → 选 A，插件思路搁置；
4. CDP 在 Work 窗口上若有意外限制（如场景隔离、target 不可见）→ 重新评估，并准备降级方案。

## 7. 重启后的探针清单（方案冻结的依据）

> 前提：用户同意带 `--remote-debugging-port=<端口>` 重启 Trae 主实例一次（任务持久化、可恢复）。

1. **CDP 连通性**：`/json` 能列出 Work 场景 target，`Runtime.evaluate` 可执行；
2. **DOM 锚点勘探**：找到稳定选择器——任务卡片列表、当前激活任务标识、聊天输入框（textarea/contenteditable）、发送/停止按钮、弹窗容器；记录为锚点清单；
3. **端到端最小闭环**：新建一个一次性测试任务 → 切到它 → 写入"回复收到"→ 发送 → 确认消息真实出现在会话中 → 用回执文件 + 按钮状态两种方式判定其完成 → 删除测试任务；
4. **后台执行验证**：仲裁者切走后，测试任务是否继续真实执行（多任务"后台并行"的关键假设，必须眼见为实）；
5. **插件命令普查**：装一次性扩展 dump 全部命令，过滤 `solo|task|agent|chat|work` 关键词，判定任务操作命令的覆盖率；
6. **弹窗清单**：主动观察/收集会打断任务的系统弹窗类型（权限、更新、网络错误），确定检测锚点与处理预案（一律 fail-stop + 升级用户，不自动点确认）；
7. **稳定性小样**：连续派发 3~5 次，统计误焦点/误判率，验证身份核对门禁有效。

探针产出：更新本文档 §6 的决策结论，并作为 `ParallelAgent实现路径.md` 的输入。

## 8. 降级方案：autoxkit + OCR

若 CDP 被未来版本封掉、且插件路线不成立：

- 用 `E:\备份\project\Python\autoxkit`（已有：窗口绑定、mss 截图、模板/颜色匹配、驱动级键鼠注入、全局 hook）+ onnxocr（拟新增）；
- **OCR 只进控制面**：会话名核对、弹窗识别、超时截图诊断；完成信号仍走回执文件；
- 已知代价：坐标/模板脆弱、Electron 窗口后台发字可能失效（文本走剪贴板粘贴）、锁屏/RDP 断开失效、需防自指焦点错乱；
- 仅作为兜底通道保留，不作为一期主方案。

## 9. 通用风险登记

| 风险 | 等级 | 缓解 |
|---|---|---|
| 误发给错误轨道 | 高 | 发送前身份断言（DOM 文本/激活态）；消息体只含文件指针；全程操作日志 |
| 仲裁者自指操作 | 高 | 控制脚本独立进程运行；断言目标窗口/任务；禁止在仲裁者自己的任务卡片上动作 |
| Trae 更新导致锚点/命令失效 | 中 | 稳定锚点优先、外置配置、fail-stop；探针每次大版本后重跑 |
| 调试端口被本机滥用 | 中 | 非默认端口、仅 127.0.0.1、用时才带参数 |
| 轨道卡死/弹窗永久挂起 | 中 | watch 超时 → 截图/DOM 诊断 → 告警升级，不盲点 |
| 空转损耗（给待命轨造活） | 中 | 沿用收缩判据，连续两批活跃轨 <2 即回归单线 |
| 锁屏后自动化失效 | 低（一期用户在场） | 文档注明前提；需要无人值守时另案处理 |
| 许可证 | 低 | autoxkit 为 GPL-3.0，编排器自用/internal 不分发；若分发需评估边界 |

## 10. 术语

- **仲裁者**：主控会话，持笔契约、派活、实检、裁决，产品口径问用户不代答。
- **轨道（T-X）**：常驻任务会话，只在自己文件领地内作业，读转达、写回执。
- **编排器**：本项目要造的自动化部件（CDP 脚本和/或扩展），仲裁者的"手"，只做控制不做决策。
- **文件信箱**：`docs/协调/` 下转达/回执/快照/手册的统称，系统唯一数据通道。
