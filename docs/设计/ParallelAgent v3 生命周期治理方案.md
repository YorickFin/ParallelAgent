# ParallelAgent v3 生命周期治理方案

- 状态：草案（待评审）
- 日期：2026-10-27
- 配套：[ParallelAgent v3 方案设计](ParallelAgent%20v3%20方案设计.md)（架构层 / 能力档案 / 执行器）
- 本文件定位：架构文档回答「怎么拆、怎么派、怎么收尾」，本文件回答「**何时拆、何时收、收回后谁做、何时交接、怎么自检**」

---

## 0. 前提

v3 的轨道默认是**一次执行**（空壳 subagent），不是常驻会话。由此推出三条贯穿全文的约束：

1. **轨道没有记忆**：每轮重新派发，身份与进度全部写在文件里（`track` / `round` / `contract_version` / `scope.paths`）
2. **没有中途观测通道**：只能拿结束回执，因此任务粒度必须能在单次执行内完成
3. **没有进程可恢复**：崩溃后只能按文件重跑，重跑即幂等

这三条决定了：生命周期治理不是「管理活着的会话」，而是「管理一串可重跑的执行」。

---

## 1. 全周期视图

```
┌─────────────────────────┐
│ 阶段 1：奠基串行         │  拆分节点前
│ 契约、骨架、边界         │  必须串行
└───────────┬─────────────┘
            │ 拆分节点：判定可拆
            ▼
┌─────────────────────────┐
│ 阶段 2：并行多轨         │  T-A/B/C/D 同批执行
│ 文件边界正交             │  分批 ≤ 能力档案上限
└───────────┬─────────────┘
            │ 收回节点：依赖收敛 / 失败率升 / 正交性消失
            ▼
┌─────────────────────────┐
│ 阶段 3：收尾串行         │  集成、验收、修补
│ 执行者按任务类型路由     │  见 §5
└─────────────────────────┘
```

三个必写节点：**拆分节点**（1→2）、**收回节点**（2→3）、**每次阶段切换**，均须更新交接手册（§6）。

---

## 2. 阶段 1：奠基串行

### 2.1 分工

**仲裁者做轻量决策（不写代码）**：

- 写契约：目标、非目标、`scope.paths`、验收口径、`contract_version`
- 设计骨架：模块边界、接口签名、文件领地划分
- 判定拆分节点：是否满足 §3.1 的前置条件

**T-0 一次性执行做重活**：

- 实现骨架代码（空目录、空接口、空测试桩）
- 跑通最小闭环
- 写第一版交接手册（供后续轨道与冷启动使用）

### 2.2 T-0 的形态

T-0 不是特殊轨道，就是**一次普通 spawn**：

- 契约里写清「只做奠基，不做业务实现」
- 产物落地后即终结，无需「销毁」概念
- 若奠基本身跨越多轮，按 §4.2 拆成多次执行，每次带上一轮产物

### 2.3 何时可跳过

- 小项目、单文件或边界明显：仲裁者可直接进入拆分节点
- 跳过时必须把「骨架假设」写进契约（后续轨道据此执行，不靠口头约定）

## 3. 拆分节点（1→2）

### 3.1 前置条件（全部满足才拆）

| 条件 | 判据 |
|---|---|
| 能力可用 | 能力档案 `max_mode` 含 L4，`max_concurrency ≥ 2` |
| 边界正交 | 各轨 `scope.paths` 无交集 |
| 可独立验收 | 每轨有独立的验收命令或判据 |
| 风险不耦合 | 任一轨失败不阻塞其余轨的验收 |
| 有收益 | 并行收益大于契约编写与实检成本 |

### 3.2 批量约束

- 同批轨道数 `batch = min(轨道数, max_concurrency)`
- 超出上限时**仲裁者自行分批**，不依赖宿主排队（超限是硬失败）
- 分批时按「依赖顺序」切：无依赖的轨先跑，有输入的轨后跑

### 3.3 拆分时必须写清

- 各轨 `scope.paths` 与产物路径
- 各轨 `contract_version`
- **收尾判据**（见 §4.3，写在契约首部或快照里）
- 本批次的 `batch` 划分

---

## 4. 阶段 2：并行执行

### 4.1 一轮的定义

**一轮 = 一次 spawn 集合**（不是「会话的一轮对话」）：

1. 仲裁者写第 N 轮契约（或复用未变更的契约）
2. 按批 spawn，每条轨只拿到：契约路径 + 回执路径 + 返回格式
3. 收齐返回（一行指针）
4. 越界扫描 → 实检 → 写快照

### 4.2 任务粒度约束

由于没有中途上报通道：

- 单条轨的任务必须能在**单次执行**内完成；做不到就拆成多轮
- 长任务在契约里必须给出「可交付的最小切片」，不允许「先跑着看」
- 一轮结束后按回执决定：继续下一轮 / 收回 / 单轨重跑

### 4.3 收尾判据（拆分时预定）

契约或快照首部必须写：

```
本轮收尾判据（任一命中即触发收回评估）：
- contract_version 达到 vX
- T-A/B/C 全部通过验收
- 出现跨轨强依赖（A 的改动波及 B）
- 累计改动行数 > N（避免无序膨胀）
- 越界扫描命中 ≥ 1 次
```

### 4.4 每轮结束后动态评估

| 判据 | 含义 | 建议阈值 |
|---|---|---|
| 剩余子任务正交性 | 各轨剩余任务是否仍互相独立 | 重叠率 > 30% → 收 |
| 强依赖链 | 某轨改动开始影响另一轨 | ≥ 1 条 → 收 |
| 执行失败率 | 本轮 spawn 失败 / 总数 | > 30% → 收 |
| 回执质量 | 实检发现的回执错误 | 连续 2 轮上升 → 收 |
| 越界命中 | scope 外写入次数 | ≥ 1 → 立即收并复核 |
| 集成验收需求 | 是否需要全局集成测试 | 出现即收 |
| 上下文压力 | 仲裁者自评接近上限（无精确计数，粗判） | 连续 2 轮「注意」以上 → 收 |

**触发规则**：连续两轮有 ≥ 2 条命中 → 收回。

### 4.5 收回不等于全部停止

- 只收回**强耦合部分**（转入阶段 3）
- 剩余正交任务可继续在当前批次跑完
- 收回决策写入快照：

```
收回决策（第 N 轮后）：
- 触发判据：<列出命中的判据>
- 剩余任务：<清单>
- 收尾路由：见 §5
```

## 5. 阶段 3：收回后由谁执行

### 5.1 四类执行者

收尾不是「把某条轨升格」，而是按任务性质选一个执行者：

| 执行者 | 适用的收尾任务 | 理由 |
|---|---|---|
| **新任仲裁者**（用户新开会话） | 集成测试、文档整理、大规模重构、需要全局视角的收束 | 上下文干净，且具备编排权 |
| **当前仲裁者** | 小修补、验收、写快照、跨轨信息已在其手上 | 信息最全，无交接成本 |
| **subagent**（一次执行） | 边界清晰的单点修改、某轨剩余工作 | 只要契约 + 最新回执即可开工 |
| **用户** | 产品口径、范围取舍、风险决策 | 不该自动化 |

### 5.2 没有「晋升」，只有执行者选择

- 轨道没有可继承的上下文，也不产生身份；不存在「把 T-A 升格为收尾者」这回事
- 若要继续某轨的剩余工作：写清契约 + 指向最新回执 → spawn 一个新的 subagent
- 新 subagent 拿到的只有文件，与从头开始无差别；所以契约必须自足，不能依赖「它应该知道」
- subagent 只能承担轨道级执行，**不能承担主控**（见 §5.3）

选择依据不是「谁最懂」，而是「收尾需要多少跨轨信息」：

| 收尾所需信息 | 执行者 |
|---|---|
| 全部在文件里，边界清晰 | subagent |
| 需要跨轮判断与取舍 | 当前仲裁者 |
| 需要全新上下文 + 编排权 | 新任仲裁者 |
| 涉及价值判断 | 用户 |

### 5.3 新任仲裁者：只能人工拉起

**结构性限制**：subagent 不能再派子代理（`nested=no`）且单次返回即结束，**不能承担主控**。因此：

- 新任仲裁者只能由**用户新开会话**产生
- 启动方式：新会话首条消息 = 「读最新交接手册，你是仲裁者 II 世，承接 T-A/B/C 收尾」
- 旧会话保留待命，用户自行决定是否关闭
- 不得引入自动拉起机制（除非宿主原生提供多级调度，属于能力档案之外的可选扩展）

### 5.4 交接成本控制

新任仲裁者只读：

1. 最新交接手册（必读）
2. `快照.md`（必读）
3. 按需读回执；**不读全部契约历史**
4. 能力档案（确认 `max_concurrency` 与 `max_mode`）

交接手册只含结构性结论，不含过程推理。

## 6. 交接手册

### 6.1 角色

- 冷启动入口：给新会话 / 新任仲裁者 / 下一轮执行使用
- **不是**过程记录（过程在契约、回执、快照里）
- 在 v3 中地位更高：轨道无状态、无进程可恢复，交接手册是唯一的「记忆索引」

### 6.2 写时机

| 节点 | 是否必写 | 内容 |
|---|---|---|
| 开轨前 | 必写 | 契约版本、各轨边界、批次划分、如何重跑 |
| 阶段切换（1→2 / 2→3） | 必写 | 阶段判据、收尾节点 |
| 收回决策时 | 必写 | 收回理由、收尾任务路由 |
| 自检告警时 | 必写 | 指标现状、推荐交接对象 |
| 用户主动要求 | 必写 | 用户指定内容 |
| 每轮结束后 | 选写 | 仅当快照发生结构性变化 |

### 6.3 版本管理

```
.parallel-agent/交接手册/
  第1版-开轨前.md
  第2版-收回决策.md
  第3版-新任仲裁者启动.md
```

每版保留不覆盖，新会话读最新版。

### 6.4 内容约束

必含：

- 当前阶段（奠基 / 并行 / 收尾）
- 当前 `contract_version`
- 各轨状态（待执行 / 已完成 / 已收回 / 已废弃）
- 欠账清单（剩余任务与对应契约路径）
- **重跑方式**（要 spawn 哪些契约、批次多大、用什么回执）
- 冷启动首条消息模板

不含：过程推理、执行细节、对话历史。

## 7. 健康度自检

### 7.1 可观测范围

v3 不依赖会话状态接口，可观测的只有：

- spawn 的返回（是否成功、是否截断、耗时）
- 回执自检字段（轨道自填）
- 越界扫描结果（文件系统比对）
- 仲裁者实检结论
- 仲裁者对自身上下文压力的粗判

不可观测：精确 token 用量、上下文剩余容量、轨道实时进度。

### 7.2 仲裁者指标

| 指标 | 含义 | 阈值 |
|---|---|---|
| 执行失败率 | 最近 N 次 spawn 失败数 / N | > 30% → 准备交接 |
| 重试次数 | 同一轨同一轮的重试次数 | ≥ 2 → 检查契约 |
| 契约版本错配 | 回执引用的版本 ≠ 当前契约版本 | ≥ 1 → 立即修正 |
| 回执实检错误 | 自己实检发现的错误 | 连续 2 轮上升 → 准备交接 |
| 重复输出 | 相同结论/契约片段重复出现 | ≥ 3 次 → 立即交接 |
| 用户否决 | 用户指出决策错误 | ≥ 2 次 → 立即交接 |
| 上下文压力 | 自评：正常 / 注意 / 警告 | 连续 2 轮注意以上 → 准备交接 |

### 7.3 轨道指标（一次性执行）

| 指标 | 含义 | 阈值 |
|---|---|---|
| 完成度 | 是否按契约产出全部文件 | 未完成 → 该轨重跑 |
| 返回截断 | 返回文本是否被裁剪 | 出现 → 改为只回路径 |
| 回执完整性 | 必备字段是否齐全 | 缺字段 → 打回重写 |
| 越界 | 是否写了 `scope.paths` 之外 | ≥ 1 → 立即收回该轨 |
| 版本错配 | 是否按最新契约执行 | 错配 → 重跑 |

### 7.4 自检报告模板

```
本轮自检（仲裁者）：
- 批次：第 N 轮 / 共 K 轨 / batch=M
- 执行失败率：x%（N 次 spawn，失败 n 次）
- 重试次数：n
- 回执实检错误：n
- 越界命中：n
- 版本错配：n
- 上下文压力：正常 / 注意 / 警告
- 健康度：良好 / 注意 / 警告
- 建议：继续 / 准备交接 / 立即收回
```

### 7.5 触发交接的条件

- 连续两轮「注意」以上
- 用户主动要求
- 阶段切换且收尾任务适合新上下文
- 出现 ≥ 2 条收回判据

## 8. 交接流程

1. 触发：自检告警 / 用户要求 / 阶段切换
2. 当前仲裁者写最新版交接手册（含重跑方式）
3. 用户新开会话
4. 新会话首条消息：读交接手册 → 承接主控（仲裁者 Skill 激活）
5. 新会话读快照 + 能力档案 → 输出接管摘要与下一步
6. 旧会话保留待命，由用户决定何时关闭

**注意**：第 3 步必须由用户执行，v3 不提供自动拉起。

## 9. 分期落地

| 能力 | 一期 | 二期 | 三期 |
|---|---|---|---|
| 奠基（阶段 1） | 用户手动 / 仲裁者直接写契约 | T-0 一次性执行 | 仲裁者自动派 T-0 |
| 拆分节点判定 | 仲裁者对判据表 | 同 + 契约自检 | 同 |
| 批次编排 | 手工分批 | Skill 按能力档案自动分批 | 同 |
| 每轮动态评估 | 仲裁者人工输出 | 模板化输出 | 指标自动汇总（仍以文件为准） |
| 收回后执行者 | 仲裁者亲自 / 用户新开会话 | 交接手册模板化 | 同 |
| 交接手册 | 关键节点手写 | 模板化生成 | 同 |
| 状态自检 | 仲裁者自评报告 | 统一模板 + 轨道自检字段 | 同 |

---

## 10. 待实践验证

1. 拆分节点判据是否需要更硬的量化标准（当前依赖仲裁者判断）
2. 收尾路由给 subagent 的边界在哪（哪些任务真的只靠契约与回执就能完成）
3. `max_concurrency` 较小（如 2-3）时，分批是否抵消并行收益
4. 越界扫描的成本（全量文件比对）在大仓库是否可接受
5. 交接手册多版本累积是否需要归档机制
6. 上下文压力自评是否足够可靠（无精确 token 计数）

## 11. 术语

- **一次性轨道**：一次 spawn 完成一轮任务，执行结束即终结
- **奠基阶段**：拆分节点前的串行任务
- **并行阶段**：多轨同批执行
- **收尾阶段**：依赖收敛后的串行任务
- **拆分节点 / 收回节点**：阶段切换时点
- **T-0**：奠基用的普通一次执行，完成后终结
- **批次**：受 `max_concurrency` 约束的一次 spawn 集合
- **重跑**：以最新契约与回执重新 spawn 某轨（不是 resume）
- **新任仲裁者**：用户新开会话承接主控
- **收尾执行者**：收回后按任务性质选定的执行者（新任仲裁者 / 当前仲裁者 / subagent / 用户）
- **交接手册**：冷启动入口，关键节点写，只含结构性结论
