# ParallelAgent 生命周期治理初稿

> 状态：**初稿**——回答 5 个动态治理问题，待实践修补
> 配套：`ParallelAgent方案定稿.md`（架构层）、本文件（生命周期层）
> 冻结日期：2026-10-15
> 适用：一期手动触发版

---

## 0. 文档定位

定稿讲"怎么拆、怎么派、怎么收工"，本文件讲"**何时拆、何时收、收回后谁做、何时该交接会话**"——多轨生命周期的动态治理。

定稿假设"拆→并行→收"是单一动作，但实际上：

- 拆分有**前置节点**（拆之前的串行奠基任务谁做？）
- 收回是**动态判定**（每轮回执后都要重新评估）
- 收回后**由谁接手**（仲裁者 vs 第二任仲裁者 vs 晋升某轨）
- 会话**状态会退化**（出错变多就要交接/新开）

实践不需要完美状态，但需要一份初稿给方向。

## 1. 串行-并行-串行的全周期视图

任务生命周期分三阶段：

```
┌─────────────────────────┐
│  阶段 1：奠基串行         │  拆分节点前
│  - 契约设计、骨架、边界   │  必须串行
│  - 谁做？见 §2            │
└───────────┬─────────────┘
            │ 拆分节点（仲裁者判定可拆）
            ▼
┌─────────────────────────┐
│  阶段 2：并行多轨         │  T-A/B/C/D 同时跑
│  - 文件边界正交           │  收益可观
│  - 何时收回？见 §3        │
└───────────┬─────────────┘
            │ 收回触发（依赖收敛 / 出错率升 / 剩余不正交）
            ▼
┌─────────────────────────┐
│  阶段 3：收尾串行         │  集成、验收、修补
│  - 谁做？见 §4            │
└─────────────────────────┘
```

**关键节点**：拆分节点（1→2）、收回节点（2→3）、阶段切换必写交接手册（见 §5）。

## 2. 阶段 1：奠基串行谁来做（问题 1）

**问题**：任务能拆，且收益可观，但拆分有节点，节点前的串行任务谁做？

### 2.1 候选方案对比

| 方案 | 优点 | 缺点 |
|---|---|---|
| 仲裁者亲自做 | 持全局视角，决策不需中转 | 干重活会撑爆上下文，无法承担主控 |
| 开"先行轨" T-0 | 仲裁者保持轻量 | T-0 的全局决策仍需仲裁者介入 |
| 用户亲自做 | 决策最准 | 违背"消灭人肉"目标 |

### 2.2 推荐分工

**仲裁者做"轻量决策"，T-0 轨做"重活实现"**：

- **仲裁者负责**（不写代码）：
  - 写契约块（最终结论嵌代码注释）
  - 设计骨架（模块边界、接口签名、文件领地划分）
  - 定义 T-A/B/C/D 各自的任务边界
  - 拆分节点判定（什么时候可以开 T-A/B/C/D）

- **T-0 轨负责**（干活）：
  - 实现骨架代码（空目录、空接口、空测试桩）
  - 跑通最小闭环（确保骨架可执行）
  - 写完交接手册（T-0 完成后自身待命或销毁）

### 2.3 T-0 的特殊性

- T-0 不是常驻轨，**完成奠基任务后销毁**或转做 T-A
- T-0 的产出（骨架代码 + 交接手册）是 T-A/B/C/D 的输入
- T-0 完成后才进入阶段 2

### 2.4 一期简化

一期可不做 T-0，由用户在仲裁者会话里手动完成奠基（写契约、定边界），然后说"开 4 轨"进入阶段 2。T-0 留二期。

## 3. 阶段 2→3：何时收回到串行（问题 2）

**问题**：何时收回？拆分时预定 + 每轮动态评估。

### 3.1 拆分时预定收尾节点

仲裁者在开轨时必须给出**收尾判据**（写在转达单首部）：

```
本轮收尾判据（任一命中即触发收回评估）：
- 契约块版本达到 v1.3.0
- T-A/B/C 全部通过验收
- 出现跨轨强依赖（T-A 改动波及 T-B）
- 总改动行数 > 1500（避免无序膨胀）
```

### 3.2 每轮回执后动态评估

仲裁者收到回执后，必须重新评估是否收回。判据：

| 判据 | 含义 | 阈值 |
|---|---|---|
| **剩余子任务正交性** | 各轨剩余任务是否还互相独立 | 重叠率 > 30% → 收 |
| **强依赖链出现** | T-A 的改动开始影响 T-B | ≥ 1 条 → 收 |
| **出错率上升** | 各轨最近 N 轮错误率 | > 30% → 收 |
| **回执质量下降** | 仲裁者实检发现的回执错误数 | 连续 2 轮上升 → 收 |
| **集成验收需求** | 是否需要全局集成测试 | 出现即收 |
| **轨活度** | 连续无新回执的轮数 | 任一轨 ≥ 2 轮 → 收 |

### 3.3 收回触发

**连续两轮有 ≥ 2 条判据命中 → 收回**。

仲裁者写"收回决策"到快照：

```
收回决策（第 5 轮后）：
- 触发判据：剩余子任务正交性（重叠 45%）+ 集成验收需求
- 剩余任务：T-A 收尾 + T-B 接入 + 全局集成测试
- 收回后由谁做：见 §4
```

### 3.4 收回不等于关闭所有轨

收回后仍有部分子任务可继续并行——只收回**强耦合部分**，剩余正交任务可继续在原轨跑。

## 4. 阶段 3：收回后由谁执行（问题 3）

**问题**：收回后由谁执行？这时仲裁者持项目信息最完整，不太应交给分轨，或由第二任仲裁者接手？

### 4.1 候选方案对比

| 方案 | 适用场景 | 优点 | 缺点 |
|---|---|---|---|
| **仲裁者亲自做** | 收尾是轻量小修补 + 验收 | 持信息最完整，无交接成本 | 上下文已用大半，做重活易爆 |
| **第二任仲裁者** | 收尾是集成测试 + 文档整理 + 大规模重构 | 上下文干净，全局视角 | 交接成本（读全部契约+快照+回执） |
| **晋升某分轨** | 收尾是该轨延续 + 小幅集成 | 已知项目细节 | 只懂自己那块，全局视角差 |
| **回归用户** | 收尾是产品口径决策 | 决策最准 | 违背"消灭人肉"目标 |

### 4.2 推荐分场景

按收尾任务类型路由：

| 收尾任务 | 推荐执行者 |
|---|---|
| 集成测试 + 文档整理 + 重构 | **第二任仲裁者**（新会话，全局视角） |
| 小修补 + 验收 + 写契约块 | **仲裁者亲自做**（轻量） |
| 某轨延续 + 小幅集成 | **晋升该轨**（继承细节） |
| 产品口径决策 + 用户偏好 | **回归用户**（不自动化） |

### 4.3 第二任仲裁者的定义

- **不是分轨晋升**，是新会话承接主控权
- 启动方式：插件新建会话 → 注入"读交接手册，你是仲裁者 II 世，承接 T-A/B/C 收尾"
- 旧仲裁者会话保留待命（如需追溯）
- 第二任仲裁者 Skill 与第一任相同（同一份 Skill）

### 4.4 交接成本控制

第二任仲裁者启动后必须读：

- `契约块.md`（最新结论）
- `快照.md`（轨/状态/欠账）
- 全部 `回执/T-X-第N轮.md`（按需）
- 旧仲裁者写的`交接手册-第N版.md`

**控制信息量**：交接手册应**只含结构性结论**，不含过程推理——避免第二任上下文也被撑爆。

### 4.5 一期简化

一期可不做第二任仲裁者：

- 收尾是轻量 → 仲裁者亲自做
- 收尾是重活 → 用户开新会话手动承接，插件不自动派发

二期再加自动第二任。

## 5. 仲裁者交接手册写时机（问题 4）

**问题**：交接手册是否每次裁决后写？或收到回执时写？

### 5.1 交接手册的角色

- 是**冷启动入口**——给新会话/新仲裁者用的
- 不是过程记录（过程在转达单/回执里）
- 是"如果当前会话死了，新会话能从哪儿接手"

### 5.2 写时机

**不需要每次裁决都写**。在关键节点必写：

| 节点 | 是否必写 | 内容 |
|---|---|---|
| 开新轨前 | 必写 | 当前契约版本 + 各轨边界 + 启动方式 |
| 阶段切换（1→2 / 2→3） | 必写 | 阶段判据 + 收尾节点 |
| 收回决策时 | 必写 | 收回理由 + 收尾任务路由 |
| 自检告警时 | 必写 | 状态指标 + 推荐交接对象 |
| 用户主动要求 | 必写 | 用户指定内容 |
| 每轮回执后 | 选写 | 仅当快照有重大变化时 |

### 5.3 版本管理

```
docs/协调/交接手册/
  第1版-开轨前.md
  第2版-收回决策.md
  第3版-第二任仲裁者启动.md
  ...
```

每版保留，不覆盖。新会话读最新版。

### 5.4 内容约束

交接手册**只含结构性结论**：

- 当前阶段（奠基/并行/收尾）
- 当前契约版本
- 各轨状态（运行/待命/已销毁）
- 欠账清单（剩余任务）
- 启动方式（新会话首条消息）

**不含**：过程推理、各轨执行细节、对话历史——这些在转达单/回执里。

## 6. 会话状态自检与交接（问题 5）

**问题**：仲裁者和分轨如何判断自身状态？出错变多后必须交接/新开。能否直接获取上下文状态？不能的话用什么指标？

### 6.1 能否直接获取上下文状态？

**不能直接获取**。Trae 不暴露：

- token 用量
- 上下文压缩次数
- 上下文剩余容量

但可获取：

- `icube.chat.getSessionRunningStatus` → "WaitingInput" / "Running"（运行态，非健康度）
- 任务列表运行图标（DOM）
- 发送按钮状态（DOM）

**健康度无官方 API**，必须用间接指标。

### 6.2 间接指标

#### 6.2.1 仲裁者健康度指标

| 指标 | 含义 | 阈值 |
|---|---|---|
| 错误率 | 最近 N 次工具调用失败次数 / N | > 30% → 准备交接 |
| 决策迟疑度 | 输出决策建议的轮数变长 | > 3 轮 → 准备交接 |
| 重复输出 | 相同代码块/结论重复出现 | ≥ 3 次 → 立即交接 |
| 回执实检错误数 | 自己实检发现的回执错误 | 连续 2 轮上升 → 准备交接 |
| 自评失败 | 用户主动指出决策错误 | ≥ 2 次 → 立即交接 |

#### 6.2.2 分轨健康度指标

| 指标 | 含义 | 阈值 |
|---|---|---|
| 工具调用错误率 | 该轨最近 N 次失败 / N | > 30% → 交接 |
| 身份断言失败 | 仲裁者核对该轨时任务名不匹配 | ≥ 2 次 → 立即交接 |
| 无新回执轮数 | 该轨连续无新回执 | ≥ 2 轮 → 交接 |
| 回执质量下降 | 仲裁者实检发现的错误 | 连续 2 轮 → 交接 |
| 自评失败 | 分轨自评无法继续 | 立即交接 |

### 6.3 一期简化

一期不做自动状态采集（无法获取 token 等），改为：

- **仲裁者每轮结束输出"自检报告"**（AI 自评，给用户参考）
- 分轨每轮回执附"自检字段"（健康度自评）
- 用户在场决定是否交接

自检报告模板：

```
本轮自检（仲裁者）：
- 错误率：12%（最近 8 次工具调用 1 次失败）
- 决策迟疑度：1 轮
- 重复输出：0 次
- 回执实检错误：0
- 健康度：良好 / 注意 / 警告
- 建议下一轮：继续 / 准备交接 / 立即交接
```

### 6.4 交接流程

1. 触发：自检告警 / 用户主动 / 阶段切换
2. 当前会话写交接手册（最新版）
3. 插件 `/new` 新会话 → 注入"读交接手册第 N 版，你是 X"
4. 旧会话保留待命，不销毁（如需追溯）
5. 插件更新身份表（sid → 角色）
6. 新会话读手册 → 承接主控/分轨身份

### 6.5 第二任仲裁者 / 第二任分轨

- 第二任仲裁者：新会话，承接主控，仲裁者 Skill 激活
- 第二任分轨（T-A II 世）：新会话，承接 T-A 身份，轨道 Skill 激活
- 旧会话保留至少 1 轮用于追溯

## 10. 术语补充

- **奠基阶段**（阶段 1）：拆分节点前的串行任务，由仲裁者+T-0 完成
- **并行阶段**（阶段 2）：T-A/B/C/D 同时跑
- **收尾阶段**（阶段 3）：依赖收敛后的串行任务
- **拆分节点**：仲裁者判定可拆的时点
- **收回节点**：仲裁者判定应收回的时点
- **T-0 轨**：奠基先行轨，非常驻，完成后销毁
- **第二任仲裁者**：新会话承接主控权
- **第二任分轨**：新会话承接某分轨身份
- **交接手册**：冷启动入口，关键节点写
- **自检报告**：AI 自评健康度，一期人工触发
