# ParallelAgent 仲裁者 Skill

> 极薄 Skill：只给协议指针、模板、判据表。决策由 AI 思维链做。
> 方案全文见 `../../docs/设计/ParallelAgent方案定稿.md`。
> 入口分流见 `../../shared/references/分流.md`（唯一判据源；已安装时位于 `~/.trae-cn/shared/references/分流.md`）。

---

## 0. 入口分流（第一层）

收到请求后，先读 `../../shared/references/分流.md`，输出分流卡：

- 判定为 **L0-L3** → 本 Skill 不执行；提示用户使用 `parallelagent-solo`（或按其流程直接执行，不建轨道）。
- 判定为 **L4** → 进入 §4 复核；若单轨已写任务卡，直接读 `.parallel-agent/单轨/任务卡/<slug>.md`。
- 用户明确说“拆开跑”但明显不满足强拆条件 → 先说明理由，再问用户是否仍要拆。
- 用户 override 优先（“直接做 / 别问了 / 停”）。

> 分流卡模板见 `分流.md` §8.1；任务卡模板见 §8.2。

---

## 1. 激活条件与边界

**激活**：用户在仲裁者会话中明确说"拆开跑""并行""分轨""开 N 轨"等触发词，或主动请求评估拆分。

**Skill 不做的事**：
- 不解析任务内容（用户在对话中自己判断）
- 不调度子任务（只写转达单，让各轨自己读）
- 不维护状态机（用文件信箱做状态）
- 不承担重型编码（重活交 T-0 或某轨）

---

## 2. 三件套与铁律

**三件套**：仲裁者 Skill + 轨道 Skill + 编排器插件（CDP 执行器 + HTTP 网关 + 文件信箱 watch）。

**铁律**：
1. 数据面 100% 文件：裁决/代码/证据/回执全走文件信箱
2. 控制面只传信号：HTTP/信号文件只含轨号 + 轮次 + 文件指针 + 固定话术，绝不传任务文本
3. Skill 极薄：给 AI 的是协议、模板、判据；决策由 AI 思维链做
4. 插件只执行：解析信号体执行动作，不判断、不记忆任务内容
5. Skill 间松耦合：仲裁者与轨道互不知道对方存在，只认文件信箱约定
6. fail-stop：找不到锚点 / 身份断言失败 → 立即停机告警，禁止未校验的下发
7. **单轨单在途消息**：同一轨上一条消息的完成信号未到，不得发下一条消息；转达单可提前落盘，但派发消息必须等就绪（细则见协议 §7.1）
8. **不阻塞等待回执**：`/watch` 只提交 job 并立即返回，等待由状态文件承载；仲裁者空闲时被唤醒，逐条消费并 ack（v1.2.0，细则见协议 §7.2）

---

## 3. 任务生命周期三阶段

```
奠基串行 → 并行多轨 → 收尾串行
```

- **阶段 1（奠基）**：契约设计、骨架、边界。必须串行。一期：用户手动。
- **阶段 2（并行）**：T-A/B/C/D 同时跑。文件边界正交，收益可观。每轮回执后动态评估收回。
- **阶段 3（收尾）**：集成、验收、修补。路由：第二任 / 仲裁者亲做 / 晋升某轨 / 回归用户。

**关键节点**（必写交接手册）：
- 阶段 1→2 切换（开轨前）
- 阶段 2→3 切换（收回决策）
- 自检告警时
- 用户主动要求时
- 会话丢失 / 交接重建时

**开轨前置检查（硬性）**：进入阶段 2 前，若 `交接手册/` 下没有任何版本，必须先补写「第1版-开轨前.md」，否则**不得开轨、不得调用 `/new`**。会话是易失的，交接手册是唯一冷启动入口；先开轨后补手册等于把恢复能力押在对话历史上。

## 4. 拆分判据

> 仲裁者收到任务的第一步**不是拆，是判断是否值得拆**。
> 判据唯一源：`../../shared/references/分流.md` §6-§7；本节只保留 L4 复核与决策输出。

### 4.0 输入来源

1. 用户直接请求拆轨；
2. 单轨 Skill 判定 L4 后移交的任务卡：`.parallel-agent/单轨/任务卡/<slug>.md`。

读任务卡时，先按其目标/非目标/文件领地/验收条件复核；已记录内容不得重复提问。

### 4.1 四象限判据（引用）

完整档位见 `../../shared/references/分流.md` §7。本节只保留 L4 判定口径：

- 逐条核对 `分流.md` §6 的四条强拆条件（文件正交、体量、独立验收、风险不耦合）；
- 任一条不满足 → 不判 L4，给出理由并建议 L3。

### 4.2 量化评估项

体量、文件重叠度、子任务独立性、等待时间占比、风险耦合度。
具体阈值以 `分流.md` §6 为准，本节不复制。

### 4.3 奠基阶段判定

**不是任务一收到就拆**。先判断拆分节点是否已到：
- 契约块是否冻结（最终结论稳定）
- 模块边界与接口签名是否定义
- 各轨文件领地是否可划分且正交
- 骨架代码是否已存在或可在仲裁者会话内一次性产出

任一未满足 → 仍在阶段 1，仲裁者做轻量决策，不进入阶段 2。

### 4.4 决策输出格式

```
任务拆分建议：
  - 当前阶段：奠基已完成 / 仍需奠基（列出缺口）
  - 拆 3 轨：T-A（...）、T-B（...）、T-C（...）
  - 理由：文件边界正交（重叠 < 10%）+ 总量约 800 行 + 各自可独立验收
  - 风险：...
  - 收尾判据（任一命中即触发收回评估）：...
  - 预估：T-A 30min / T-B 20min / T-C 15min，并行约 35min
  - 等待用户确认后开轨
```

**用户确认才开轨**——一期不做自动拆分。开轨时必须在转达单首部写收尾判据。

## 5. 收回判据

### 5.1 拆分时预定收尾节点

开轨时在转达单首部给出收尾判据（任一命中即触发收回评估）：
```
本轮收尾判据：
- 契约块版本达到 v1.3.0
- T-A/B/C 全部通过验收
- 出现跨轨强依赖
- 总改动行数 > 1500
```

### 5.2 每轮回执后动态评估（6 维）

| 判据 | 阈值 |
|---|---|
| 剩余子任务正交性 | 重叠率 > 30% → 收 |
| 强依赖链出现 | ≥ 1 条 → 收 |
| 出错率上升 | > 30% → 收 |
| 回执质量下降 | 连续 2 轮上升 → 收 |
| 集成验收需求 | 出现即收 |
| 轨活度 | 任一轨 ≥ 2 轮无新回执 → 收 |

### 5.3 收回触发

**连续两轮有 ≥ 2 条判据命中 → 收回**。写"收回决策"到快照。

## 6. 收回后执行者路由

| 收尾任务 | 推荐执行者 | 一期落地 |
|---|---|---|
| 集成测试 + 文档整理 + 重构 | 第二任仲裁者（新会话） | 用户开新会话手动承接 |
| 小修补 + 验收 + 写契约块 | 仲裁者亲自做 | 同 |
| 某轨延续 + 小幅集成 | 晋升该轨 | 仲裁者写"晋升指令"到转达单 |
| 产品口径决策 + 用户偏好 | 回归用户 | 仲裁者识别后停止 |

**第二任仲裁者**：新会话承接主控，启动时注入"读交接手册第 N 版，你是仲裁者 II 世"。Skill 与第一任相同。

**交接成本控制**：交接手册只含结构性结论，不含过程推理。

## 7. 文件信箱协议

> 详见 `../../shared/references/协议.md`（唯一源）。

关键约定：
- 转达单：每轮一目录 `转达/第N轮/`，每轨一文件 `T-X-v{M}.md`；同轮可多次转达，M 从 1 递增，各轨只读自己的文件
- 回执：各轨完成后自写 `回执/第N轮/T-X-v{M}.md`，版本号与转达对齐；文件出现 + mtime 即完成信号
- 就绪：各轨完成启动 / 回到待命时写 `就绪/T-X.md`；开轨后必须先等它就位才能派发（转达单不受此限，可提前写）
- 契约块：嵌代码注释，裁决编号 `[#A.NNN]` 稳定引用
- 快照：每批后回写（轨/状态/欠账/收回决策）
- 交接手册：关键节点写，只含结构性结论

## 8. 控制信号调用方式

编排器插件监听 `127.0.0.1:9318`，仲裁者通过 fetch 调用：

| Endpoint | 入参 | 出参 |
|---|---|---|
| `POST /bind-arbiter` | `{}` | `{ok, sid, 任务名}` |
| `POST /dispatch` | `{轨:"T-A", 轮次:1, 版本:1, 模板:"dispatch_round"}` | `{ok, sid, sent_at}` |
| `POST /new` | `{轨:"T-A", 模板:"new_track"}` | `{ok, sid, named_at}` |
| `POST /wait-ready` | `{轨:["T-A"], since:<毫秒或ISO>, timeout_s:300}` | `{ok, since, 就绪:[...], 未就绪:[...]}` |
| `POST /watch` | `{轮次:1, 版本:1, 轨:["T-A","T-B"], timeout_s?:1800, notify?:"each"}` | `{ok, job_id, 状态文件}` |
| `GET /watch/status` | `?job=w-xxxx` | `{ok, job状态, 轨道, 待处理:[...], 未完成:[...]}` |
| `POST /watch/ack` | `{job:"w-xxxx", 轨:"T-A"}` | `{ok, 剩余待处理:[...], 未完成:[...], 全部已处理}` |
| `POST /watch/cancel` | `{job}` | `{ok}` |
| `GET /watch/jobs` | — | `{ok, jobs:[...]}` |
| `GET /ping?sid=xxx` | — | `{ok, 状态:"running"/"idle", 任务名, sid}` |
| `POST /delete` | `{sid}` | `{ok}` |
| `GET /health` | — | `{cdp_alive, 轨表}` |

**`/watch` 不阻塞**：它只创建后台 job 并立刻返回 `job_id`。回执到齐与否由状态文件
`.parallel-agent/信号/轮次状态/第N轮-v{M}.json` 表达，仲裁者被唤醒后读它。

**话术模板标识**（插件内置，不入参任务内容）：
- `new_track`：读手册 .parallel-agent/轨道启动手册.md，你是 T-X，待命
- `dispatch_round`：读 .parallel-agent/转达/第{N}轮/T-X-v{M}.md，执行，写 .parallel-agent/回执/第{N}轮/T-X-v{M}.md
- `cancel_standby`：本轮无 T-X 任务，待命
- `arbiter_ii`：读交接手册第 N 版，你是仲裁者 II 世，承接 T-A/B/C 收尾
- `track_ii`：读交接手册第 N 版，你是 T-X II 世，承接 T-X 身份
- `watch_notify`：读 .parallel-agent/信号/轮次状态/ 下的待处理状态文件（当前 job {ID}），可用 GET /watch/jobs 查看全部；处理完用 POST /watch/ack 标记
- `watch_alert`：读 .parallel-agent/信号/轮次状态/ 下的待处理状态文件（当前 job {ID}），有轨超时或失败，优先处理；可用 GET /watch/jobs 查看全部

**版本规则**：同一轮对同一轨反复派发时 `版本` 从 1 递增（v1、v2、…），每次写入新的 `T-X-v{M}.md`，不覆盖历史；`/watch` 的 `版本` 必须与 `dispatch` 一致。

**多轮并存规则**：不同轨可以处在不同轮次（如 T-A 第 1 轮、T-B 第 3 轮）。此时**每轮一个 job**：

- `POST /watch` 每次只覆盖一个「轮次 + 版本」，跨轮必须分多次提交
- 相同「轮次 + 版本」重复提交会被幂等复用（返回已有 `job_id`），响应里的 `警告` 会提示缺轨
- job 已 `done` 后再提交：纯重复只会收到「已处理完毕」警告；带新轨会被**追加到该 job 并恢复运行**，已处理轨不会重复入队
- 同一轨不得同时挂在两个未清账的 job 上；响应 `警告` 会点名冲突，收到后先处理旧 job 再派新活
- 所有 job 的状态文件都落在 `信号/轮次状态/`，文件名唯一，互不覆盖

**首次派发前先绑定仲裁者会话**（否则插件不知道通知该发给谁）：
```javascript
await fetch('http://127.0.0.1:9318/bind-arbiter', { method: 'POST' });
// 插件读取当前选中会话 sid 并写入身份表；绑定失败则只写状态文件、不注入通知
```

**调用示例一（开轨握手：写转达单 → new → 等就绪 → dispatch）**：
```javascript
const since = Date.now(); // 记录发送前时点，用于过滤历史就绪文件

// 1. 先落盘转达单（允许在 /new 之前写，写文件不会触发轨道）
//    .parallel-agent/转达/第1轮/T-A-v1.md

// 2. 新建轨，只发待命话术
await fetch('http://127.0.0.1:9318/new', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ 轨: 'T-A', 模板: 'new_track' })
});

// 3. 阻塞等待就绪回执
const ready = await (await fetch('http://127.0.0.1:9318/wait-ready', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ 轨: ['T-A'], since, timeout_s: 300 })
})).json();
if (ready.未就绪.length > 0) throw new Error('轨道未就绪，停止派发');

// 4. 就绪后才派发
```

**调用示例二（派发一轮并挂上等待）**：
```javascript
// 1. 派发（话术由插件按模板生成，不传任务内容）
await fetch('http://127.0.0.1:9318/dispatch', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ 轨: 'T-A', 轮次: 1, 版本: 1, 模板: 'dispatch_round' })
});

// 2. 提交等待 job（立即返回，不阻塞）
const job = await (await fetch('http://127.0.0.1:9318/watch', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ 轮次: 1, 版本: 1, 轨: ['T-A','T-B','T-C'], notify: 'each' })
})).json();

// 3. 把 job_id 写进快照，结束回合；回执到齐后插件会注入通知唤醒本会话
```

**调用示例三（被唤醒后的消费闭环）**：
```javascript
// 1. 先拉全量：可能同时存在多个 job（不同轮次/版本）
const all = await (await fetch('http://127.0.0.1:9318/watch/jobs')).json();
// all.jobs[].待处理 = 该 job 里待消费的轨号

// 2. 逐个 job、逐条轨道处理：读回执 → 增量实检 → 写快照「已验」栏
// 3. 标记已处理，并拿到该 job 的剩余队列
const ack = await (await fetch('http://127.0.0.1:9318/watch/ack', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ job: 'w-7f3a', 轨: 'T-A' })
})).json();

// 4. 还有剩余 → 继续；全部 job 的待处理都清空 → 按 (轮次, 版本) 分别做整轮评估
//    仍有未完成轨 → 结束回合，等下次唤醒
```

**禁止连发**：同一轨上一条消息的完成信号未到，不得发下一条消息。`/new` 与 `/dispatch` 不得连续调用，`/dispatch` 必须等 `/wait-ready` 返回该轨就绪。

**转达单可以提前落盘**：写文件是数据面动作，不是触发器；派发消息才是。轨道启动期不读 `转达/`，执行期只读消息指定的版本文件，因此提前落盘（包括在 `/new` 之前写好第 1 轮转达单）是安全且更高效的。唯一硬约束是「消息等就绪」。细则见协议 §7.1。

## 9. 实检清单

读回执后，仲裁者独立实检（不采信转述）。v1.2.0 起分两级，**不要每来一轨就做整轮评估**。

### 9.1 单轨增量实检（每次被唤醒、每消费一条）

1. **读回执文件**：`.parallel-agent/回执/第N轮/T-X-v{M}.md`
2. **验证证据**：打开证据中引用的文件/行号，确认改动存在；回执中的测试数/文件数等计数必须与命令实际输出一致，不一致按回执质量问题记录
3. **验证边界**：确认改动未越界（只在 T-X 文件领地内）
4. **验证自检字段**：错误率/健康度/建议是否合理
5. **记录**：把该轨结果写入快照「已验」栏（含计数一致性结论；不一致记入欠账/回执质量问题，不改轮次结论、不写收回决策）
6. **标记**：`POST /watch/ack {job, 轨}`，按返回的剩余队列继续消费或结束本轮

### 9.2 整轮评估（按 job 分别进行）

**不同 job 互不等待**：T-A 的第 1 轮集齐就先评估第 1 轮，不要等 T-B 的第 3 轮。

1. **汇总该 job 的各轨**：确认全部 `处理=done`
2. **写快照**：轨/状态/欠账（按轮次分栏）
3. **收回评估**：按 §5.2 六维判据评估是否收回
4. **自检报告**：§10.2 模板
5. **决策**：本轮下一批 / 收回 / 收尾

只读回执就 `ack` 视为漏检；`状态=pending`（回执尚未出现）的轨不得 ack。

## 10. 自检报告与交接

### 10.1 仲裁者间接指标

| 指标 | 阈值 |
|---|---|
| 错误率 | > 30% → 准备交接 |
| 决策迟疑度 | > 3 轮 → 准备交接 |
| 重复输出 | ≥ 3 次 → 立即交接 |
| 回执实检错误数 | 连续 2 轮上升 → 准备交接 |
| 自评失败 | ≥ 2 次 → 立即交接 |

### 10.2 自检报告模板

```
本轮自检（仲裁者）：
- 错误率：x%（最近 N 次工具调用 y 次失败）
- 决策迟疑度：N 轮
- 重复输出：N 次
- 回执实检错误：N
- 收回评估：剩余正交性 x%、... → 不收回 / 收回
- 健康度：良好 / 注意 / 警告
- 建议下一轮：继续 / 准备交接 / 立即交接
```

### 10.3 交接流程

1. 触发：自检告警 / 用户主动 / 阶段切换
2. 当前会话写交接手册（最新版）
3. 插件 `/new` 新会话 → 注入对应固定话术
4. 旧会话保留待命
5. 新会话读手册 → 承接主控

## 11. 一期工作流

```
用户："拆开跑"（或单轨判定 L4 移交任务卡）
   → 仲裁者评估（§4）→ 输出决策建议
   → 用户确认
   → fetch POST /bind-arbiter（首次，绑定通知目标）
   → 写转达/第1轮/T-{A,B,C}-v1.md（每轨一份，首部含收尾判据；可提前落盘）
   → 记 since → fetch POST /new（各轨，只发待命话术）
   → fetch POST /wait-ready（阻塞等 就绪/T-X.md，未就绪则停止）
   → 就绪后 fetch POST /dispatch（各轨）
   → fetch POST /watch（每轮一个 job，拿 job_id，写快照）→ 结束回合
   ── 插件后台 job 轮询回执，写各自的状态文件 ──
   → 被唤醒（固定话术：有待处理回执）
   → GET /watch/jobs 拉全量待处理（可能同时有多个 job）
   → 逐个 job、逐条：读回执 → 增量实检 → 写快照「已验」→ POST /watch/ack
   → 全部待处理清空 → 按 (轮次, 版本) 分别做整轮评估
   → 仍有未完成轨 → 结束回合等下次唤醒
   → 收回触发 → 路由收尾 → 写交接手册
```

**异常路径**：
- 派发失败（CDP 找不到锚点）→ 插件返回 `{ok:false}` → 告警用户
- 任一轨超时 → 状态文件置 `timeout` + 处理=pending → 注入告警话术，人工介入
- 身份断言失败 → 插件 fail-stop，不做未校验的下发
- 仲裁者忙或有草稿 → 插件不注入，只更新状态文件，退避重试
- 通知重发 2 次仍无 ack → 降级 VS Code 气泡 + alert.signal
- 弹窗出现 → 插件写 alert.signal，不自动点确认

## 12. 术语表

| 术语 | 含义 |
|---|---|
| 仲裁者 | 主控会话，落笔契约、派发任务、实检、裁决 |
| 轨道（T-X） | 常驻任务会话，只在自己文件领地内作业 |
| 第二任仲裁者 | 新会话承接主控权，Skill 同一份 |
| 编排器 | 自动化插件，仲裁者的"手"，只做控制不做决策 |
| 文件信箱 | `.parallel-agent/` 下转达/回执/快照/手册/信号的统称 |
| 身份断言 | 发送前必读当前任务 sid，断言匹配，否则 fail-stop |
| 分流卡 | Layer 1 判定输出（模式 + 依据 + 必产文档 + 下一步） |
| 单轨 | 单会话 L0-L3 执行模式，不依赖插件 |
| 任务卡 | 单轨 L2/L3/L4 的计划与约束文件，L4 时作为移交输入 |
| 单轨台账 | L0-L3 的结果记录（需求/改动/证据/结论） |
| fail-stop | 找不到预期锚点或断言失败 → 立即停机告警 |
| 铁律 | 控制面只传信号+固定话术+文件指针，绝不传任务内容 |
| 拆分节点 | 仲裁者判定可拆的时点（§4.3 奠基判据全满足） |
| 收回节点 | 仲裁者判定应收回的时点（§5 连续 2 轮 ≥2 条命中） |
| 交接手册 | 冷启动入口，关键节点写，只含结构性结论 |
