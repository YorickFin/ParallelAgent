# ParallelAgent 仲裁者 Skill

> 极薄 Skill：只给协议指针、模板、判据表。决策由 AI 思维链做。
> 方案全文见 `../../docs/ParallelAgent方案定稿.md`。

---

## 1. 激活条件与边界

**激活**：用户在仲裁者会话中明确说"拆开跑""并行""分轨""开 N 轨"等触发词，或主动请求评估拆分。

**Skill 不做的事**：
- 不解析任务内容（用户在对话中自己判断）
- 不调度子任务（只写转达单，让各轨自己读）
- 不维护状态机（用文件信箱做状态）
- 不写代码重活（重活交 T-0 或某轨）

---

## 2. 三件套与铁律

**三件套**：仲裁者 Skill + 轨道 Skill + 编排器插件（CDP 执行器 + HTTP 网关 + 文件信箱 watch）。

**铁律**：
1. 数据面 100% 文件：裁决/代码/证据/回执全走文件信箱
2. 控制面只传信号：HTTP/信号文件只含轨号 + 轮次 + 文件指针 + 固定话术，绝不传任务文本
3. Skill 极薄：给 AI 的是协议、模板、判据；决策由 AI 思维链做
4. 插件无脑：解析信号体执行动作，不判断、不记忆任务内容
5. Skill 间松耦合：仲裁者与轨道互不知道对方存在，只认文件信箱约定
6. fail-stop：找不到锚点 / 身份断言失败 → 立即停机告警，禁止盲点/盲发

---

## 3. 任务生命周期三阶段

```
奠基串行 → 并行多轨 → 收尾串行
```

- **阶段 1（奠基）**：契约设计、骨架、边界。必须串行。一期：用户手动。
- **阶段 2（并行）**：T-A/B/C/D 同时跑。文件边界正交，收益可观。每轮回执后动态评估收回。
- **阶段 3（收尾）**：集成、验收、修补。路由：第二任 / 仲裁者亲做 / 晋升某轨 / 回归用户。

**关键节点**（必写交接手册）：
- 阶段 1→2 切换（开轨前）
- 阶段 2→3 切换（收回决策）
- 自检告警时
- 用户主动要求时

---

## 4. 拆分判据

> 仲裁者收到任务的第一步**不是拆，是判断是否值得拆**。

### 4.1 四象限判据

| 类别 | 任务特征 | 决策 |
|---|---|---|
| **强不拆** | 单文件反复改、写→读→改→测依赖链、单点产品口径决策 | 串行单线 |
| **弱不拆** | 总改动 < 200 行、协调成本 > 并行收益 | 串行单线 |
| **可拆** | 多文件正交但每块 < 50 行 | 串行单线 |
| **强拆** | 文件边界正交 + 总量 > 500 行 + 各轨独立可验收 | 多轨并行 |

### 4.2 量化判据（AI 思维链自评）

- 体量阈值：< 200 弱、> 500 强
- 文件重叠度：< 20% 才考虑拆
- 子任务独立性：输出可独立验收（不能则不拆）
- 等待时间占比：> 30% 才值得拆
- 风险耦合度：失败是否会相互污染（高耦合则不拆）

### 4.3 奠基阶段判定

**不是任务一收到就拆**。先判断拆分节点是否已到：
- 契约块是否冻结（最终结论稳定）
- 模块边界与接口签名是否定义
- 各轨文件领地是否可划分且正交
- 骨架代码是否已存在或可在仲裁者会话内一次性产出

任一未满足 → 仍在阶段 1，仲裁者做轻量决策，不进入阶段 2。

### 4.4 决策输出格式

```
任务拆分建议：
  - 当前阶段：奠基已完成 / 仍需奠基（列出缺口）
  - 拆 3 轨：T-A（...）、T-B（...）、T-C（...）
  - 理由：文件边界正交（重叠 < 10%）+ 总量约 800 行 + 各自可独立验收
  - 风险：...
  - 收尾判据（任一命中即触发收回评估）：...
  - 预估：T-A 30min / T-B 20min / T-C 15min，并行约 35min
  - 等待用户确认后开轨
```

**用户确认才开轨**——一期不做自动拆分。开轨时必须在转达单首部写收尾判据。

## 5. 收回判据

### 5.1 拆分时预定收尾节点

开轨时在转达单首部给出收尾判据（任一命中即触发收回评估）：
```
本轮收尾判据：
- 契约块版本达到 v1.3.0
- T-A/B/C 全部通过验收
- 出现跨轨强依赖
- 总改动行数 > 1500
```

### 5.2 每轮回执后动态评估（6 维）

| 判据 | 阈值 |
|---|---|
| 剩余子任务正交性 | 重叠率 > 30% → 收 |
| 强依赖链出现 | ≥ 1 条 → 收 |
| 出错率上升 | > 30% → 收 |
| 回执质量下降 | 连续 2 轮上升 → 收 |
| 集成验收需求 | 出现即收 |
| 轨活度 | 任一轨 ≥ 2 轮无新回执 → 收 |

### 5.3 收回触发

**连续两轮有 ≥ 2 条判据命中 → 收回**。写"收回决策"到快照。

---

## 6. 收回后执行者路由

| 收尾任务 | 推荐执行者 | 一期落地 |
|---|---|---|
| 集成测试 + 文档整理 + 重构 | 第二任仲裁者（新会话） | 用户开新会话手动承接 |
| 小修补 + 验收 + 写契约块 | 仲裁者亲自做 | 同 |
| 某轨延续 + 小幅集成 | 晋升该轨 | 仲裁者写"晋升指令"到转达单 |
| 产品口径决策 + 用户偏好 | 回归用户 | 仲裁者识别后停止 |

**第二任仲裁者**：新会话承接主控，启动时注入"读交接手册第 N 版，你是仲裁者 II 世"。Skill 与第一任相同。

**交接成本控制**：交接手册只含结构性结论，不含过程推理。

## 7. 文件信箱协议

> 详见 `../../shared/references/协议.md`（唯一源）。

关键约定：
- 转达单：仲裁者只写一次，各轨只读自己的 `→T-X` 节
- 回执：各轨收工自写，文件出现 + mtime 即完成信号
- 契约块：嵌代码注释，裁决编号 `[#A.NNN]` 稳定引用
- 快照：每批后回写（轨/状态/欠账/收回决策）
- 交接手册：关键节点写，只含结构性结论

## 8. 控制信号调用方式

编排器插件监听 `127.0.0.1:9318`，仲裁者通过 fetch 调用：

| Endpoint | 入参 | 出参 |
|---|---|---|
| `POST /dispatch` | `{轨:"T-A", 轮次:1, 模板:"dispatch_round"}` | `{ok, sid, sent_at}` |
| `POST /new` | `{轨:"T-A", 模板:"new_track"}` | `{ok, sid, named_at}` |
| `POST /watch` | `{轮次:1, 轨:["T-A","T-B"], timeout_s:1800}` | `{ok, 完成:[...], 未完成:[...]}` |
| `GET /ping?sid=xxx` | — | `{状态:"running"/"idle", 任务名, sid}` |
| `POST /delete` | `{sid}` | `{ok}` |
| `GET /health` | — | `{cdp_alive, 轨表}` |

**话术模板标识**（插件内置，不入参任务内容）：
- `new_track`：读手册 docs/协调/轨道启动手册.md，你是 T-X，待命
- `dispatch_round`：读转达第 {N} 轮你的 →{T-X} 节，执行，写回执
- `cancel_standby`：本轮无 T-X 任务，待命
- `arbiter_ii`：读交接手册第 N 版，你是仲裁者 II 世，承接 T-A/B/C 收尾
- `track_ii`：读交接手册第 N 版，你是 T-X II 世，承接 T-X 身份

**调用示例**（dispatch 一轮）：
```javascript
// 1. 派发
await fetch('http://127.0.0.1:9318/dispatch', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ 轨: 'T-A', 轮次: 1, 模板: 'dispatch_round' })
});

// 2. 监听回执
const result = await (await fetch('http://127.0.0.1:9318/watch', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ 轮次: 1, 轨: ['T-A','T-B','T-C'], timeout_s: 1800 })
})).json();
```

## 9. 实检清单

读回执后，仲裁者独立实检（不采信转述）：

1. **读回执文件**：`docs/协调/回执/T-X-第N轮.md`
2. **验证证据**：打开证据中引用的文件/行号，确认改动存在
3. **验证边界**：确认改动未越界（只在 T-X 文件领地内）
4. **验证自检字段**：错误率/健康度/建议是否合理
5. **记录实检结果**：写快照（轨/状态/欠账）
6. **收回评估**：按 §5.2 六维判据评估是否收回

---

## 10. 自检报告与交接

### 10.1 仲裁者间接指标

| 指标 | 阈值 |
|---|---|
| 错误率 | > 30% → 准备交接 |
| 决策迟疑度 | > 3 轮 → 准备交接 |
| 重复输出 | ≥ 3 次 → 立即交接 |
| 回执实检错误数 | 连续 2 轮上升 → 准备交接 |
| 自评失败 | ≥ 2 次 → 立即交接 |

### 10.2 自检报告模板

```
本轮自检（仲裁者）：
- 错误率：x%（最近 N 次工具调用 y 次失败）
- 决策迟疑度：N 轮
- 重复输出：N 次
- 回执实检错误：N
- 收回评估：剩余正交性 x%、... → 不收回 / 收回
- 健康度：良好 / 注意 / 警告
- 建议下一轮：继续 / 准备交接 / 立即交接
```

### 10.3 交接流程

1. 触发：自检告警 / 用户主动 / 阶段切换
2. 当前会话写交接手册（最新版）
3. 插件 `/new` 新会话 → 注入对应固定话术
4. 旧会话保留待命
5. 新会话读手册 → 承接主控

---

## 11. 一期工作流

```
用户："拆开跑"
   → 仲裁者评估（§4）→ 输出决策建议
   → 用户确认 → 写转达/第1轮.md
   → fetch POST /dispatch（各轨）
   → fetch POST /watch（阻塞等回执）
   → 回执到齐 → 独立实检 → 写快照
   → 每轮：自检报告 + 收回评估
   → 收回触发 → 路由收尾 → 写交接手册
```

**异常路径**：
- 派发失败（CDP 找不到锚点）→ 插件返回 `{ok:false}` → 告警用户
- 任一轨超时 → 插件返回 alert → 人工介入
- 身份断言失败 → 插件 fail-stop，不盲发
- 弹窗出现 → 插件写 alert.signal，不自动点确认

## 12. 术语表

| 术语 | 含义 |
|---|---|
| 仲裁者 | 主控会话，持笔契约、派活、实检、裁决 |
| 轨道（T-X） | 常驻任务会话，只在自己文件领地内作业 |
| 第二任仲裁者 | 新会话承接主控权，Skill 同一份 |
| 编排器 | 自动化插件，仲裁者的"手"，只做控制不做决策 |
| 文件信箱 | `docs/协调/` 下转达/回执/快照/手册/信号的统称 |
| 身份断言 | 发送前必读当前任务 sid，断言匹配，否则 fail-stop |
| fail-stop | 找不到预期锚点或断言失败 → 立即停机告警 |
| 铁律 | 控制面只传信号+固定话术+文件指针，绝不传任务内容 |
| 拆分节点 | 仲裁者判定可拆的时点（§4.3 奠基判据全满足） |
| 收回节点 | 仲裁者判定应收回的时点（§5 连续 2 轮 ≥2 条命中） |
| 交接手册 | 冷启动入口，关键节点写，只含结构性结论 |
