# ParallelAgent v1.2.0 设计文档

> 状态：**核心链路已实施（v1.2.0 分支），待真机实测与发布**
> 前置：v1.1.0（一键安装 + 就绪握手 + 版本化信箱）已发布
> 范围：只改「回执等待与通知」这一条链路，不动拆分判据、收回判据、信箱文件格式

---

## 1. 问题

v1.1.0 的 `/watch` 是**阻塞式** HTTP：仲裁者 `fetch` 后一直挂到回执到齐或超时（默认 1800 秒）。

这在 Chat 会话里必然失效：

| 环节 | 实际情况 |
|---|---|
| 工具调用时长 | 有上限（Shell 最长 600 秒），30 分钟的请求会被截断或转后台 |
| AI 回合 | 一次阻塞结束即回合结束，**没有任何事件会把它唤醒** |
| 结果 | 仲裁者「派发完就退出」，回执到齐也无人处理；后续实检、快照、下一轮全部停摆 |

结论：**阻塞等待与 Chat 会话的回合模型不兼容**。等待与通知必须从 AI 的调用栈里搬出去。

---

## 2. 目标与非目标

### 2.1 目标

1. 派发后仲裁者可以结束回合，等待状态在插件进程里持续存在。
2. 回执一到就进入「待处理队列」，仲裁者一空闲就收到通知并开始消费。
3. 仲裁者消费完一条后自己标记，同时拿到剩余队列，**在同一回合内连续消费**，不被通知打断。
4. 多轨陆续完成时不产生通知风暴，也不漏掉超时/失败。
5. 不覆盖用户草稿、不无限切换会话。

### 2.2 非目标

- 不做自动拆分、自动收回（仍由仲裁者 AI 决策）
- 不改转达单/回执/快照/契约块格式
- 不让插件解析回执内容（插件只认文件存在 + mtime）
- 不做跨宿主的推送通道（仍依赖 CDP 注入）

---

## 3. 关键决策（已与用户对齐）

| 决策点 | 结论 |
|---|---|
| 等待状态归属 | **插件进程**（job），与 AI 回合解耦 |
| `/watch` 语义 | 由「阻塞等待」改为「提交 job 并立即返回 `job_id`」 |
| 待处理信号 | **状态文件** `信号/轮次状态/第N轮-v{M}.json` 是唯一真相源 |
| 通知触发条件 | 有 `处理=pending` 的项 **且** 仲裁者空闲 **且** 输入框为空 |
| 输入框为空检查 | **保留**（用户确认），有草稿绝不注入，宁可延后 |
| 消费方式 | 仲裁者处理完一条 → `POST /watch/ack` → 响应直接带回剩余队列 |
| 状态粒度 | 三级：`pending → notified → done`，另设 `null` 表示无需处理 |
| 逐轨 vs 全齐 | 逐轨入队（`notify=each`，默认），全齐聚合作为可选项 |
| 空闲探测 | 两级：任务行图标（无侵入）→ `status()` 二次确认（仅在注入前） |

## 4. 总体架构

```
仲裁者会话                编排器插件                              轨道会话
    │                        │                                       │
    │ POST /watch            │                                       │
    │───────────────────────>│ 创建 job（内存 + 状态文件）             │
    │<───────────────────────│ {job_id, 状态文件指针}                 │
    │                        │                                       │
    │ 结束回合                │ 后台每 pollInterval 扫描 mtime          │
    │                        │<────────────────────── 回执落盘 ───────│
    │                        │ 更新状态文件：done + 处理=pending       │
    │                        │                                       │
    │                        │ tick：有待处理？ → 探测空闲 → 注入话术   │
    │<───────────────────────│ 固定话术（job_id + 文件指针）            │
    │ 新回合开始              │                                       │
    │ 读状态文件 → 读回执      │                                       │
    │ 增量实检 → 写快照        │                                       │
    │ POST /watch/ack        │                                       │
    │───────────────────────>│ 处理=done，返回剩余队列                 │
    │<───────────────────────│ {剩余待处理:[...], 未完成:[...]}        │
    │ 剩余非空 → 继续消费      │                                       │
    │ 剩余为空 → 整轮评估 → 结束回合                                    │
```

三个新增组件：

| 组件 | 职责 | 不做 |
|---|---|---|
| `WatchJobManager` | job 表、后台轮询、轨状态机、状态文件原子写与恢复 | 不解析回执内容、不判断任务对错 |
| `Notifier` | 空闲探测、输入框判空、注入固定话术、冷却与重发、失败降级 | 不携带任务文本、不重试盲发 |
| `状态文件` | 待处理队列的真相源，仲裁者消费凭据 | 不是过程记录 |

## 5. 状态文件 schema

路径：`.parallel-agent/信号/轮次状态/第N轮-v{M}.json`（`信号/` 已在 `.gitignore`，不入版本库）

```json
{
  "job": "w-7f3a",
  "轮次": 1,
  "版本": 1,
  "job状态": "running",
  "仲裁者": "a1b2c3d4e5f6a7b8c9d0e1f2",
  "notify": "each",
  "创建于": "2026-10-24T11:55:02+08:00",
  "更新于": "2026-10-24T11:58:07+08:00",
  "轨道": {
    "T-A": {
      "状态": "done",
      "回执": ".parallel-agent/回执/第1轮/T-A-v1.md",
      "mtime": "2026-10-24T11:58:03+08:00",
      "处理": "notified",
      "通知于": "2026-10-24T11:58:05+08:00",
      "重发次数": 0,
      "处理于": null
    },
    "T-B": {
      "状态": "pending",
      "回执": null,
      "mtime": null,
      "处理": null,
      "通知于": null,
      "重发次数": 0,
      "处理于": null
    },
    "T-C": {
      "状态": "timeout",
      "回执": null,
      "mtime": null,
      "处理": "pending",
      "通知于": null,
      "重发次数": 0,
      "处理于": null
    }
  }
}
```

### 5.1 字段语义

| 字段 | 取值 | 含义 |
|---|---|---|
| `轨道.X.状态` | `pending` / `done` / `timeout` / `failed` | 轨道本身干完没有；`failed` 保留给 watcher 异常 |
| `轨道.X.处理` | `null` / `pending` / `notified` / `done` | 仲裁者的消费进度 |
| `job状态` | `running` / `done` / `cancelled` | job 生命周期 |
| `notify` | `each` / `all` | 逐轨入队 / 全齐入队 |

### 5.2 处理状态机

```
       回执稳定出现 / 超时
null ────────────────────────> pending ──注入成功──> notified ──ack──> done
                                 ^                       │
                                 └──重发失败降级/用户清空──┘
```

必须保留 `notified`：注入后、仲裁者尚未 ack 的窗口里，若只有 `pending/done` 两态，下个 tick 会看到它仍空闲而重复注入同一回执，多轨陆续完成时会造成重复唤醒。

### 5.3 写入规则

- **插件是唯一写者**。仲裁者只通过 HTTP 让插件写，禁止直接编辑状态文件（避免并发写坏）。
- 原子写：先写 `*.tmp` 再 `rename` 覆盖。
- 插件重启后从 `信号/轮次状态/*.json` 恢复所有 `job状态=running` 的 job，继续轮询，不丢等待。

## 6. 入队规则（多轨陆续完成）

### 6.1 逐轨入队（默认 `notify=each`）

每轨回执稳定出现（连续 2 次 mtime 相同）→ 立刻：

1. 该轨 `状态=done`、`处理=pending`
2. 写状态文件
3. 进入通知候选（同一 tick 内完成的多轨合并成一次通知）

### 6.2 全齐入队（可选 `notify=all`）

轨级完成只写 `状态=done`、`处理=null`；**全部轨进入终态**（`done` / `timeout` / `failed`）时统一置 `处理=pending`，只通知一次。

适用：各轨工作量相当、希望一次性做整轮评估。代价是慢轨拖住全局。

### 6.3 异常优先

`timeout` / `failed` 一经判定即置 `处理=pending`，并在话术上使用 `watch_alert` 模板，**不等其余轨**。满足 `notify=all` 时也例外立即入队。

### 6.4 合并窗口

同一 tick 内产生的多个 `pending` 合并为一次注入；`pending` 项数不设上限，仲裁者一次消费多轨。

## 7. 通知器设计

### 7.1 触发条件（全部满足才注入）

```
1) 存在 处理=pending 的项，或 处理=notified 且距上次通知 ≥ 重发阈值
2) 无 running 迹象（L1）
3) status() === idle（L2）
4) 输入框文本为空
5) 距上次注入 ≥ 冷却时间（默认 3s，重发退避 60s / 120s）
```

### 7.2 两级空闲探测

| 级别 | 方式 | 侵入性 | 用途 |
|---|---|---|---|
| L1 | 读任务行内的运行图标：`.task-list-row-wrapper[data-session-id="<仲裁者 sid>"]` 内是否存在 `svg.trae-icon-TaskState_running` | 无 | 每 tick 过滤掉明显在跑的会话 |
| L2 | `navigateTo(仲裁者 sid)` → `status()` === `idle` | 切一次会话 | 仅在即将注入时做最终确认 |

L1 命中「无图标」只代表**疑似空闲**，必须用 L2 兜底，避免把「等待输入 / 刚结束未收尾」误判为可注入。

### 7.3 注入与最小打扰

1. 记录注入前用户选中的 `sid`。
2. `navigateTo` 仲裁者 → `assertIdentity` 仲裁者 sid → 确认输入框为空 → `insertText` 固定话术 → `send`。
3. **注入后切回原 sid**，让用户视图不跳走；仲裁者的新回合在后台继续执行（已实测后台可跑，见定稿 §8.6）。
4. 注入成功 → 相关项 `处理=notified`、`通知于=now`，写状态文件。

### 7.4 重发与降级

| 情况 | 动作 |
|---|---|
| `notified` 超过 120s 仍未 ack，且仲裁者空闲 | 重发一次，`重发次数+1`；最多 2 次 |
| 重发 2 次仍无 ack | 降级：VS Code 通知气泡 + `alert.signal`，不再注入 |
| 输入框有草稿 | 不注入，保持 `pending`，60s 退避后重试 |
| 仲裁者 running | 不注入，下个 tick 再看（退避至 15s） |
| 注入失败（锚点/身份断言） | fail-stop：写 `alert.signal` + 气泡，不盲发、不重试 |

## 8. HTTP API 变更

### 8.1 端点表

| Endpoint | 入参 | 出参 | 动作 |
|---|---|---|---|
| `POST /watch` | `{轮次, 版本, 轨:[...], timeout_s?, notify?: "each"\|"all"}` | `{ok, job_id, 状态文件}` | 创建后台 job，**立即返回** |
| `GET /watch/status` | `?job=w-7f3a` | `{ok, job状态, 轨道, 待处理:[...], 未完成:[...]}` | 只读查询 |
| `POST /watch/ack` | `{job, 轨}` | `{ok, 剩余待处理:[...], 未完成:[...], 全部已处理:bool}` | 标记 `处理=done`，带回剩余队列 |
| `POST /watch/cancel` | `{job}` | `{ok}` | 取消 job，停止轮询并清理 |
| `POST /bind-arbiter` | `{}` | `{ok, sid, 任务名}` | 把**当前选中会话**绑定为仲裁者 |
| `GET /watch/jobs` | — | `{ok, jobs:[...]}` | 列出全部 job（自检/恢复用） |

### 8.2 兼容与废弃

- 旧阻塞式 `POST /watch` 的语义被替换；v1.1.0 的 `{完成, 未完成}` 结构不再返回。
- `POST /wait-ready`、`/new`、`/dispatch`、`/ping`、`/delete`、`/health` 不变。
- 仲裁者必须 `POST /bind-arbiter` 成功后才能收到通知；未绑定时只写状态文件，不注入。

### 8.3 仲裁者 sid 绑定

```
仲裁者在首次派发前：POST /bind-arbiter
→ 插件读当前选中会话 sid + 任务名，写入身份表.仲裁者
→ 之后每次注入前用 assertIdentity 二次校验
```

用户在仲裁者会话里说「拆开跑」的那一刻，选中态必然在该会话上，因此这次绑定可靠。绑定失效（sid 被删）→ 注入 fail-stop，提示重新绑定。

### 8.4 新增固定话术

| 场景 | 话术 |
|---|---|
| 回执待处理通知 | `读 .parallel-agent/信号/轮次状态/第{N}轮-v{M}.json（job {ID}），有待处理回执；处理完用 POST /watch/ack 标记` |
| 超时/失败告警 | `读 .parallel-agent/信号/轮次状态/第{N}轮-v{M}.json（job {ID}），有轨超时或失败，优先处理` |

话术只含轮次、版本、job id 与文件指针，不含任何任务内容，符合铁律。

## 9. 仲裁者行为变更

### 9.1 派发后

```
写转达单 → /new → /wait-ready → /dispatch（各轨）
→ POST /watch {轮次, 版本, 轨, notify}
→ 拿到 job_id，记录到快照
→ 结束回合（不再阻塞等待）
```

### 9.2 被唤醒后（消费闭环）

```
读状态文件 → 取 处理=pending/notified 的第一条
→ 读该轨回执
→ 增量实检（只验该轨：证据、边界、自检字段）
→ 写快照「已验」栏
→ POST /watch/ack {job, 轨}
      ├─ 剩余待处理非空 → 继续取下一条（不结束回合）
      └─ 剩余为空      → 若仍有未完成轨 → 结束回合等下次唤醒
                        └─ 全轨终态 → 整轮评估（收回六维）→ 写快照 → 决定下一轮或收尾
```

### 9.3 两级实检（防止碎片化）

| 时机 | 动作 | 不做什么 |
|---|---|---|
| 单轨完成（每次唤醒） | 该轨**增量实检**，记录到快照的「已验」栏 | 不写收回决策、不改轮次结论 |
| 全轨终态 | **整轮评估**：收回判据六维、收尾判据、下一轮决策 | 不重复逐轨实检 |

如果没有这个分层，逐轨唤醒会让仲裁者在「每来一轨就评估一次收回」，把整轮判断切碎，甚至误触发收回。

### 9.4 硬约束

- `ack` 必须发生在该轨的实检记录写入快照**之后**；只读回执就 ack 视为漏检。
- 同一轨的 `ack` 幂等：重复调用返回同样结果，不报错。
- 禁止 ack 一个 `状态=pending`（回执尚未出现）的轨。

## 10. 时序：三轨陆续完成

```
t=00:30  T-A done    → 处理=pending；无 running → idle → 注入 #1
t=00:32  仲裁者 ack  → 剩余=[] ；结束回合
t=00:35  T-B done    → 处理=pending → 注入 #2
t=00:36  仲裁者 ack  → 剩余=[] ；结束回合
t=01:10  T-C timeout → 处理=pending（alert）→ 立即注入 #3
t=01:12  仲裁者 ack  → 剩余=[] ；未完成=[] → 整轮评估
```

若 T-B 与 T-C 在合并窗口内同时到达，则只注入一次，仲裁者一次消费两条。

## 11. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 注入切走用户会话 | 打断当前浏览 | 注入后切回原 sid |
| 清空用户草稿 | 丢失输入 | 判空检查（已保留），有草稿一律不注入 |
| 通知风暴 | 上下文膨胀、用户烦躁 | `notified` 态 + 合并窗口 + 冷却 + 重发上限 |
| 逐轨唤醒切碎整轮判断 | 误收回 | §9.3 两级实检分层 |
| 任务行图标语义不明 | 误判空闲 | L2 `status()` 二次确认兜底 |
| 插件重载丢 job | 回执无人处理 | 状态文件恢复 + `GET /watch/jobs` |
| Trae DOM 变更 | 注入失败 | fail-stop + alert.signal，不盲发 |
| 仲裁者 ack 后忘了继续 | 队列积压 | ack 响应直接带回剩余队列，Skill 规定非空继续 |

## 13. 验收标准

1. 派发后仲裁者回合正常结束，插件侧 job 持续运行。
2. 单轨回执落盘后，在仲裁者空闲且输入框为空的前提下，5 秒内收到注入通知。
3. 三轨在 3 分钟内陆续完成，注入次数 ≤ 3，且每次只带一条固定话术。
4. 仲裁者 ack 后，状态文件中该轨 `处理=done`；ack 响应包含剩余队列。
5. 仲裁者输入框有草稿时不注入，草稿内容不被清空。
6. 插件窗口重载后，未完成的 job 能从状态文件恢复并继续轮询。
7. `timeout` 触发时立即注入告警话术，不等其余轨。
8. 注入失败（锚点缺失/身份不符）时写入 `alert.signal`，不重复盲发。

## 14. 待实测项

实施前必须实测，结果回写本文档：

1. 任务行 running 图标在「刚结束、待输入」时是否消失——决定 L1 的误报率。
2. 输入框判空：`.chat-input-v2-input-box-editable` 的 `innerText` 在空白时是否为 `''`。
3. 注入并切回原会话后，仲裁者新回合是否仍正常执行（预期可以，§8.6 已证后台可跑）。
4. 仲裁者 `running` 期间收到注入消息的行为（预期会排队或丢弃，本设计不依赖该路径）。
