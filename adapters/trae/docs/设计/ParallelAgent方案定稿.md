## 1. 目标与范围

### 1.1 目标

把个人实战中已验证的"仲裁者 + 多轨 + 文件留痕"并行开发模式迁移到 Trae Work，**免去用户手工转发消息**环节：仲裁者会话通过自动化编排层自行派发任务、完成判定，用户只在产品口径决策与异常升级时介入。

### 1.2 非目标（明确不做）

- 不用 UI 自动化传递工作内容（裁决/代码/证据一律走文件）；
- 不做跨机分布式、不做多用户；
- 不追求 7×24 无人值守，一期只覆盖"用户在场的并行开发批次"；
- 一期不做自动判定拆分（仅手动触发 + 仲裁者给理由）；
- 一期不做第二任仲裁者自动派发、不做 T-0 奠基轨自动化。

### 1.3 一期范围

- 交付两个 Skill：仲裁者 Skill、轨道 Skill
- 交付一个插件（A+B 合一）：CDP 执行器 + HTTP 网关 + 文件信箱 watch
- 触发方式：**仅手动触发**（用户说"拆开跑"才进入多轨流程）
- 用户不在场时不自动开轨
- 状态自检靠 AI 自评报告，不靠自动采集

## 2. 总体架构

### 2.1 三件套 + 数据/控制面分离

```
┌──────────────── 数据面（100% 文件，可溯源）────────────────┐
│  契约块（嵌代码注释） 转达/第N轮/T-X-v{M}.md  回执/第N轮/T-X-v{M}.md │
│  快照.md  轨道启动手册.md  交接手册/第N版-*.md  信号/*.{sig,ack} │
└─────────────────────────────────────────────────────────────┘
              ▲ 仲裁者用原生文件工具直接读             ▲ 各轨自读自写
              │                                       │
┌─────────────┴──────────────┐         ┌──────────────┴──────────┐
│  仲裁者会话（主控）         │         │  轨道会话 T-A/B/C/D      │
│  - 决策：是否拆 / 拆几轨    │         │  - 读自己的转达节        │
│  - 落笔：契约/转达/快照     │         │  - 执行                  │
│  - 调编排器（只发控制信号） │         │  - 写回执                │
│  - 实检、裁决               │         │                          │
└─────────────┬──────────────┘         └──────────────▲──────────┘
              │ 控制面（HTTP / 信号文件）              │
              │ 仅含：轨号 + 轮次 + 文件指针            │
              ▼                                       │
        ┌─────────────────────────────────────────────────────┐
        │  编排器插件（A + B 合一）                              │
        │  - HTTP 网关（B）：仲裁者 fetch 调用                  │
        │  - CDP 执行器（A）：建/切/派/删/状态查询              │
        │  - 文件信箱 watch：回执出现 + mtime → 信号           │
        │  - 纯执行：只解析控制信号，不解析任务内容           │
        └─────────────────────────────────────────────────────┘
```

### 2.2 三件套职责

| 部件 | 角色 | 关键能力 | 不做的事 |
|---|---|---|---|
| **仲裁者 Skill** | 决策+落笔+实检 | 判拆分、写契约/转达/快照、发控制信号、读回执独立实检、每轮动态评估收回 | 不直接发会话消息、不切会话、不承担重型编码 |
| **轨道 Skill** | 接收任务 + 执行 + 回执 | 读转达节、执行任务、写回执、回执附自检字段 | 不读别轨转达、不直接调插件、不决策 |
| **编排器插件** | 纯执行器 | CDP 操作 + HTTP 网关 + 文件 watch + 身份表持久化 | 不解析任务内容、不决策、不记忆任务内容 |

### 2.3 铁律

1. **数据面 100% 文件**：裁决/代码/证据/回执全走文件信箱
2. **控制面只传信号**：HTTP/信号文件只含 `轨号 + 轮次 + 文件指针 + 固定话术`，绝不传任务文本
3. **Skill 极薄**：Skill 给 AI 的是协议、模板、判据；决策由 AI 思维链做
4. **插件只执行**：解析信号体执行动作，不判断、不记忆任务内容
5. **Skill 间松耦合**：仲裁者 Skill 与轨道 Skill 互不知道对方存在，只认文件信箱约定
6. **fail-stop**：找不到锚点 / 身份断言失败 → 立即停机告警，禁止未校验的下发

### 2.4 三阶段生命周期视图（引用）

任务生命周期分三阶段：**奠基串行 → 并行多轨 → 收尾串行**。何时切换、收回后谁做、交接手册何时写、会话状态如何自检，详见 `ParallelAgent生命周期治理初稿.md` §1-§6。本文档 §3-§6 只引结论用于架构层落位。

## 3. 任务生命周期三阶段

> 详细判据与方案对比见 `生命周期治理初稿.md` §1-§2。本节只固定阶段边界。

```
┌─────────────────────────┐
│  阶段 1：奠基串行         │  拆分节点前
│  - 契约设计、骨架、边界   │  必须串行
│  - 仲裁者轻量决策 + T-0 重活 │  一期：用户手动 / 二期：T-0 自动
└───────────┬─────────────┘
            │ 拆分节点（仲裁者判定可拆，用户确认才开轨）
            ▼
┌─────────────────────────┐
│  阶段 2：并行多轨         │  T-A/B/C/D 同时跑
│  - 文件边界正交           │  收益可观
│  - 每轮回执后动态评估收回   │
└───────────┬─────────────┘
            │ 收回触发（依赖收敛 / 出错率升 / 剩余不正交 / 集成需求）
            ▼
┌─────────────────────────┐
│  阶段 3：收尾串行         │  集成、验收、修补
│  - 路由：第二任 / 仲裁者亲做 │  晋升某轨 / 回归用户
│  - 一期：用户开新会话手动承接 │
└─────────────────────────┘
```

**关键节点**（必写交接手册）：
- 阶段 1→2 切换（开轨前）
- 阶段 2→3 切换（收回决策）
- 自检告警时
- 用户主动要求时

**一期简化**：
- 阶段 1：用户在仲裁者会话里手动完成奠基（写契约、定边界、写骨架），T-0 留二期
- 阶段 3：收尾是轻量 → 仲裁者亲做；收尾是重活 → 用户开新会话手动承接；第二任仲裁者自动派发留二期

## 4. 拆分判据

> 仲裁者收到任务的第一步**不是拆，是判断是否值得拆**。

### 4.1 四象限判据

| 类别 | 任务特征 | 决策 |
|---|---|---|
| **强不拆**（必须串行） | 单文件反复改、写→读→改→测依赖链、单点产品口径决策、前步输出是后步输入 | 串行单线 |
| **弱不拆**（可拆但不值得） | 总改动 < 200 行、单文件单点修改、协调成本 > 并行收益 | 串行单线 |
| **可拆**（边界明确但小） | 多文件正交但每块都 < 50 行，单线也很快 | 串行单线 |
| **强拆**（值得开轨） | 文件边界正交 + 总量 > 500 行 + 各轨独立可验收；或 等待确成瓶颈 | 多轨并行 |

### 4.2 量化判据（AI 思维链自评）

仲裁者 Skill 在判断时输出以下评估：

- **体量阈值**：预估改动行数（< 200 弱、> 500 强）
- **文件重叠度**：子任务涉及文件的重叠率（< 20% 才考虑拆）
- **子任务独立性**：输出是否可独立验收（不能则不拆）
- **等待时间占比**：跑测/编译/外部依赖等待占比（> 30% 才值得拆）
- **风险耦合度**：失败是否会相互污染（高耦合则不拆）

### 4.3 奠基阶段判定（拆分节点是否存在）

**不是任务一收到就拆**。仲裁者必须先判断**拆分节点是否已到**：

- 契约块是否冻结（最终结论稳定）
- 模块边界与接口签名是否定义
- 各轨文件领地是否可划分且正交
- 骨架代码是否已存在或可在仲裁者会话内一次性产出

任一未满足 → 仍在阶段 1，仲裁者做轻量决策（写契约/定边界/出骨架），不进入阶段 2。

### 4.4 决策输出格式

仲裁者不直接拆，而是给用户一个**决策建议**：

```
任务拆分建议：
  - 当前阶段：奠基已完成 / 仍需奠基（列出缺口）
  - 拆 3 轨：T-A（前端 UI 重构）、T-B（后端 API 调整）、T-C（测试用例补全）
  - 理由：文件边界正交（重叠 < 10%）+ 总量约 800 行 + 各自可独立验收
  - 风险：T-B 改 API 后 T-A 需同步对接，已在转达单中标注依赖时序
  - 收尾判据（任一命中即触发收回评估）：契约版本达 v1.3.0 / T-A/B/C 全部验收 / 总改动 > 1500 行
  - 预估：T-A 30min / T-B 20min / T-C 15min，并行总时长约 35min（串行需 65min）
  - 等待用户确认后开轨
```

**用户确认才开轨**——一期不做自动拆分。开轨时必须在转达单首部写**收尾判据**（见 §5.1）。

## 5. 收回判据

> 详细判据表见 `生命周期治理初稿.md` §3。本节只固定实现层。

### 5.1 拆分时预定收尾节点

仲裁者在开轨时必须在转达单首部给出**收尾判据**（任一命中即触发收回评估）：

```
本轮收尾判据：
- 契约块版本达到 v1.3.0
- T-A/B/C 全部通过验收
- 出现跨轨强依赖（T-A 改动波及 T-B）
- 总改动行数 > 1500（避免无序膨胀）
```

### 5.2 每轮回执后动态评估（6 维）

仲裁者收到回执后**必须重新评估是否收回**，不能只看预定的收尾判据：

| 判据 | 含义 | 阈值 |
|---|---|---|
| 剩余子任务正交性 | 各轨剩余任务是否还互相独立 | 重叠率 > 30% → 收 |
| 强依赖链出现 | T-A 的改动开始影响 T-B | ≥ 1 条 → 收 |
| 出错率上升 | 各轨最近 N 轮错误率 | > 30% → 收 |
| 回执质量下降 | 仲裁者实检发现的回执错误数 | 连续 2 轮上升 → 收 |
| 集成验收需求 | 是否需要全局集成测试 | 出现即收 |
| 轨活度 | 连续无新回执的轮数 | 任一轨 ≥ 2 轮 → 收 |

### 5.3 收回触发

**连续两轮有 ≥ 2 条判据命中 → 收回**。仲裁者写"收回决策"到快照：

```
收回决策（第 5 轮后）：
- 触发判据：剩余子任务正交性（重叠 45%）+ 集成验收需求
- 剩余任务：T-A 收尾 + T-B 接入 + 全局集成测试
- 收回后由谁做：见 §6
```

### 5.4 部分收回

收回不等于关闭所有轨。**只收回强耦合部分**，剩余正交任务可继续在原轨跑——一期可简化为全收回，部分收回留二期验证。

## 6. 收回后执行者路由

> 详细方案对比见 `生命周期治理初稿.md` §4。本节固定路由表。

按收尾任务类型路由：

| 收尾任务 | 推荐执行者 | 一期落地 |
|---|---|---|
| 集成测试 + 文档整理 + 重构 | **第二任仲裁者**（新会话，全局视角） | 用户开新会话手动承接，插件不自动派发 |
| 小修补 + 验收 + 写契约块 | **仲裁者亲自做**（轻量） | 同 |
| 某轨延续 + 小幅集成 | **晋升该轨**（继承细节） | 仲裁者写"晋升指令"到转达单，该轨继续 |
| 产品口径决策 + 用户偏好 | **回归用户**（不自动化） | 仲裁者识别后停止，等用户决策 |

**第二任仲裁者定义**：新会话承接主控，启动时注入"读交接手册第 N 版，你是仲裁者 II 世，承接 T-A/B/C 收尾"，仲裁者 Skill 与第一任相同（同一份 Skill）。旧会话保留待命。

**交接成本控制**：交接手册只含结构性结论（当前阶段/契约版本/各轨状态/欠账/启动方式），**不含过程推理**——避免第二任上下文被撑爆。第二任按需读 `回执/第N轮/T-X-v{M}.md`。

## 7. Skill 设计

### 7.1 仲裁者 Skill

**激活条件**：用户在仲裁者会话中明确说"拆开跑""并行""分轨""开 N 轨"等触发词，或主动请求评估拆分。

**Skill 内容（极薄）**：

- 拆分判据表（§4.1）+ 量化判据（§4.2）+ 奠基阶段判定（§4.3）
- 决策输出模板（§4.4）
- 收回判据（§5）+ 收尾判据模板
- 收回后执行者路由表（§6）
- 文件信箱协议（见 `references/协议.md`）
- 控制信号调用方式（HTTP 调插件）
- 实检清单（读回执后的验证步骤）
- 自检报告模板（见 §11）
- 交接手册写时机表（见 §9.4）

**Skill 不做**：

- 不解析任务内容（用户在对话中自己判断）
- 不调度子任务（只写转达单，让各轨自己读）
- 不维护状态机（用文件信箱做状态）
- 不承担重型编码（重活交 T-0 或某轨）

**典型对话流程**：

1. 用户："把这个任务拆开跑"
2. 仲裁者 Skill 引导 AI 用判据表评估 → 输出决策建议（含收尾判据）
3. 用户确认 → 仲裁者写 `转达/第1轮/T-{A,B,C}-v1.md`（每轨一份；允许提前落盘）
4. 记 `since` → fetch `/new` 开轨（只发待命话术）
5. fetch `/wait-ready` 等各轨写出 `就绪/T-X.md`（未就绪则停止，不派发）
6. 就绪后 fetch `/dispatch` 派发
7. 仲裁者 fetch 插件 HTTP `/watch` 监听回执
8. 回执到齐 → 仲裁者独立实检 → 写快照 → 每轮输出自检报告 + 收回评估 → 决策下一轮/收回

> 铁律：同一轨同一时刻只允许一条在途**消息**。转达单属于数据面，可提前落盘；`/dispatch` 必须等 `/wait-ready` 返回就绪。

### 7.2 轨道 Skill

**激活条件**：新会话首条消息永远是"读手册，你是 T-X，待命"——由插件注入。

**Skill 内容（极薄）**：

- 信箱协议（同仲裁者，引用同一份 `references/协议.md`）
- 任务接收模板：读 `转达/第N轮/T-X-v{M}.md`（每轨独立文件，无需解析他轨分节）
- 执行原则：只在自己文件领地内作业
- 回执模板：引用裁决编号 + 证据形式 + 完成时点 + 自检字段
- 不读别轨转达文件的纪律
- 自检字段模板（见 §11）

**Skill 不做**：

- 不直接调插件
- 不与其他轨通信
- 不做决策（只执行转达节里的任务）

### 7.3 第二任仲裁者 Skill

- 与第一任**同一份 Skill**，不另立
- 启动方式：插件 `/new` 新建会话 → 注入"读交接手册第 N 版，你是仲裁者 II 世，承接 T-A/B/C 收尾"
- 旧仲裁者会话保留待命，不销毁（如需追溯）
- 第二任启动后必须读：契约块 + 快照 + 旧仲裁者写的交接手册（按需读各回执）

### 7.4 Skill 间共享 reference

两个 Skill 都引用同一份 `references/协议.md`，内容：

- 文件信箱目录结构（含交接手册目录）
- 转达单格式（含收尾判据首部）
- 回执格式（含自检字段）
- 契约块格式
- 快照格式（含收回决策块）
- 交接手册格式
- 控制信号格式

避免两个 Skill 各自定义导致版本漂移。

## 8. 编排器插件设计（A + B 合一）

### 8.1 整体形态

一个本地 VS Code 风格扩展，装入 Trae 扩展宿主：

- **常驻 HTTP 服务**（B 部）：监听 127.0.0.1:9318
- **CDP 调用层**（A 部）：通过 WebSocket 连 Trae 调试端口 9317
- **文件 watch**：监听 `.parallel-agent/信号/*.signal` 与 `.parallel-agent/回执/`
- **身份表持久化**：sid → 角色（仲裁者/T-X）映射，存插件 storage

### 8.2 HTTP API（仲裁者 Skill 调用）

| Endpoint | 入参 | 出参 | 动作 |
|---|---|---|---|
| `POST /dispatch` | `{轨: "T-A", 轮次: 1, 版本: 1, 话术文件指针}` | `{ok, sid, sent_at}` | CDP 切到 T-A → 身份断言 → 注入话术 → 发送 |
| `POST /new` | `{轨: "T-A", 手册文件指针}` | `{ok, sid, named_at}` | CDP 新建任务 → 注入首条消息 → 发送 → 落身份表 |
| `POST /wait-ready` | `{轨:["T-A"], since, timeout_s:300}` | `{ok, 就绪:[...], 未就绪:[...]}` | 阻塞等待就绪回执（开轨握手用，允许阻塞） |
| `POST /watch` | `{轮次, 版本, 轨:[...], timeout_s?, notify?}` | `{ok, job_id, 状态文件, 复用, 警告}` | **提交后台 job 并立即返回**（v1.2.0 不再阻塞）；同轮次版本幂等复用 |
| `GET /watch/status` | `?job=` | `{ok, job状态, 轨道, 待处理, 未完成}` | 只读查询待处理队列 |
| `POST /watch/ack` | `{job, 轨}` | `{ok, 剩余待处理, 未完成, 全部已处理}` | 标记该轨已消费，带回剩余队列 |
| `POST /watch/cancel` | `{job}` | `{ok}` | 取消 job 并清理 |
| `GET /watch/jobs` | — | `{ok, jobs:[...]}` | 列出全部 job（自检/恢复） |
| `POST /bind-arbiter` | `{}` | `{ok, sid, 任务名}` | 绑定当前选中会话为仲裁者（通知目标） |
| `GET /ping?sid=xxx` | sid | `{状态: "running"/"idle", 任务名}` | CDP 读状态 |
| `POST /delete` | `{sid}` | `{ok}` | CDP 菜单序列删除 |
| `GET /health` | — | `{cdp_alive, port, 轨表}` | 自检 |

**所有 endpoint 入参不含任务内容**——只含轨号、轮次、文件指针。

### 8.2.1 等待与通知（v1.2.0）

阻塞式 `/watch` 与 Chat 会话的回合模型不兼容：工具调用有时长上限，回合结束即无人接收结果。因此 v1.2.0 把等待从 AI 调用栈搬到插件进程：

1. `POST /watch` 只**提交 job** 并立即返回 `job_id`，仲裁者随后结束回合。
2. job 在插件侧持续轮询回执 mtime，维护状态文件 `信号/轮次状态/第N轮-v{M}.json`（待处理队列的唯一真相源）。
3. 通知器每 tick 判断：存在 `处理=pending` **且** 仲裁者空闲 **且** 输入框为空 → 注入固定话术唤醒仲裁者；注入后切回用户原会话。
4. 仲裁者处理完一轨 → `POST /watch/ack` → 响应带回剩余队列；非空则同一回合继续消费，为空则结束回合。
5. 空闲探测三级：`status()` 读当前会话（L0）→ 任务行运行图标排除（L1，**图标仅在会话未选中时显示**）→ `status()` 二次确认（L2，仅注入前）。
6. 超时/失败立即入队并按告警话术通知；多轨同 tick 完成做合并窗口，避免通知风暴。
7. **多轮并存**：不同轨可处于不同轮次，按「每轮一个 job」拆分；各 job 的状态文件独立，同轮次版本重复提交幂等复用。仲裁者被唤醒后先 `GET /watch/jobs` 拉全量，再逐 job 逐条 ack。

完整设计见 `ParallelAgent-v1.2.0设计文档.md`。

### 8.5 方案 B 失败实证（已证伪独立路线）

`icube.chat.sendToAgentNonBlocking` 在扩展宿主里执行时报错：

```
Validating data failed: project_id: Validation error:
length [{"min": Number(1), "value": String("")}]
```

**根因**：扩展宿主无当前项目上下文，`project_id` 为空字符串。

**严重副作用**：尽管 RPC 返回失败，**消息却通过 fallback 路径发到了 IDE 当前选中会话**——会话被污染且 AI 卡死。

**结论**：插件无法独立用命令发消息，必须走 CDP。B 部只承担 HTTP 网关 + 文件 watch + 只读命令（`getSessionRunningStatus` 可用）。

### 8.6 后台并行假设（已实测）

通过合成 `.click()` 切换 `.taskItem`：
- `.taskItemSelected` 与顶部任务名同步变化；
- **切走后，原 Agent 的工具调用仍继续返回**；
- 结论：**Work 多任务切走后仍在后台执行**——这是并行多轨的前提。

### 8.7 安全前提

- 调试端口只绑 `127.0.0.1`，非默认 9317（不用 9222）
- 编排器不工作时**不带**调试端口启动 Trae
- Chromium 不能热附加，需 `restart-with-debug.ps1`（WMI 脱离进程树拉起）先关再开
- 端口暴露面 = 完整操控 IDE，必须管控
- 扩展改 package.json 必须 bump 版本号 + 全量重启 Trae（Page.reload 不刷新扫描缓存）

## 9. 文件信箱协议

### 9.1 目录结构

```
.parallel-agent/
  轨道启动手册.md            # 新会话首条消息永远指向它
  转达/第N轮/T-X-v{M}.md     # 仲裁者按轨独立写（首部含收尾判据；同轮可多次转达，M 从 1 递增）
  回执/第N轮/T-X-v{M}.md     # 各轨完成后自写（含自检字段，与转达对称）
  就绪/T-X.md                # 轨道完成启动、进入待命时自写（开轨握手信号）
  快照.md                    # 仲裁者每批后回写：轨/状态/欠账/收回决策
  契约块.md                  # 嵌代码注释形式的最终结论
  交接手册/
    第1版-开轨前.md          # 关键节点写，冷启动入口
    第2版-收回决策.md
    第3版-第二任仲裁者启动.md
    ...
  信号/
    dispatch.signal          # 仲裁者→插件：派发指令
    dispatch.ack             # 插件→仲裁者：已派发
    watch.ack                # 插件→仲裁者：回执到齐
    alert.signal             # 插件→仲裁者：超时/卡死告警
    ping.signal              # 仲裁者→插件：查状态
    ping.ack                 # 插件→仲裁者：状态回报
```

### 9.2 转达单格式

每轮一个目录 `转达/第N轮/`；每轨一个独立文件 `T-X-v{M}.md`。同一轮可对同一轨多次转达（v1、v2、…），便于修订/追加而不覆盖历史。

```markdown
# T-X · 第 N 轮 · v{M} 转达

## 收尾判据（任一命中即触发收回评估；各轨一致）
- 契约块版本达到 v1.3.0
- T-A/B/C 全部通过验收
- 出现跨轨强依赖
- 总改动行数 > 1500

## 快照
- 当前契约版本：v1.2.3
- 关键文件状态：[简要列表]

## 任务（T-X 专属）
[任务边界、目标、文件领地、验收形式]

## 时序约束
- （若有依赖）T-A 完成后本轨才能开始
```

### 9.3 回执格式

```markdown
# T-X · 第 N 轮 · v{M} 回执

- 裁决编号引用：[#A.001]
- 完成时点：2026-10-15T10:41:00+08:00
- 证据形式：[文件路径 + 行号 / 测试通过 / 截图]
- 命令与计数：[本次实际执行的验收命令 → 输出摘要]
- 实际改动：[文件列表]
- 待仲裁者实检：[验证清单]

## 自检
- 错误率：x%（最近 N 次工具调用 y 次失败）
- 自评健康度：良好 / 注意 / 警告
- 建议下一轮：继续 / 准备交接 / 立即交接
```

**回执文件的出现与 mtime 即完成信号**——编排器轮询 `回执/第N轮/` 目录即可，原则上不读 UI 输出。回执版本号 v{M} 与对应转达版本号对齐。

### 9.4 交接手册

**角色**：冷启动入口——给新会话/第二任仲裁者用的，不是过程记录。

**写时机**（详见 `生命周期治理初稿.md` §5，这里只列示）：

| 节点 | 是否必写 | 内容 |
|---|---|---|
| 开新轨前 | 必写 | 当前契约版本 + 各轨边界 + 启动方式 |
| 阶段切换（1→2 / 2→3） | 必写 | 阶段判据 + 收尾节点 |
| 收回决策时 | 必写 | 收回理由 + 收尾任务路由 |
| 自检告警时 | 必写 | 状态指标 + 推荐交接对象 |
| 用户主动要求 | 必写 | 用户指定内容 |
| 每轮回执后 | 选写 | 仅当快照有重大变化时 |

**内容约束**：只含结构性结论（当前阶段/契约版本/各轨状态/欠账/启动方式），**不含**过程推理、各轨执行细节、对话历史。

**版本管理**：每版保留不覆盖，新会话读最新版。

### 9.5 控制信号格式

`dispatch.signal`（仲裁者→插件）：
```json
{
  "batch": 1,
  "actions": [
    { "type": "new", "轨": "T-A", "手册指针": ".parallel-agent/轨道启动手册.md" }
  ]
}
```

派发必须等 `就绪/T-A.md` 出现后另发一批：
```json
{
  "batch": 2,
  "actions": [
    { "type": "dispatch", "轨": "T-A", "话术": "读 .parallel-agent/转达/第1轮/T-A-v1.md，执行，写 .parallel-agent/回执/第1轮/T-A-v1.md" }
  ]
}
```

**信号体只含轨号 + 轮次 + 文件指针 + 固定话术模板，绝不含任务内容**。

**单轨单在途消息**：同一轨上一条**消息**的完成信号未到，不得发下一条消息。转达单是数据面动作、不是触发器，可提前落盘（含 `/new` 之前）；`/dispatch` 必须等就绪。完成信号：新建轨 → `就绪/T-X.md`；派发轮次 → `回执/第N轮/T-X-v{M}.md`；取消待命 → `就绪/T-X.md` 刷新。

**等待信号（v1.2.0）**：回执到齐不再通过阻塞请求或 `watch.ack` 表达，而是写入状态文件 `信号/轮次状态/第N轮-v{M}.json`。每轨两个维度：`状态`（pending/done/timeout/failed）与 `处理`（null/pending/notified/done）。插件只认文件存在 + mtime，不解析回执内容。

### 9.6 固定话术模板

控制面绝不传裁决内容，只用以下固定模板：

- **新建轨首条**：`读手册 .parallel-agent/轨道启动手册.md，你是 T-X，待命`
- **派发轮次**：`读 .parallel-agent/转达/第 {N} 轮/T-X-v{M}.md，执行，写 .parallel-agent/回执/第 {N} 轮/T-X-v{M}.md`
- **取消待命**：`本轮无 T-X 任务，待命`
- **第二任仲裁者启动**：`读交接手册第 N 版 .parallel-agent/交接手册/第N版-*.md，你是仲裁者 II 世，承接 T-A/B/C 收尾`
- **第二任分轨启动**：`读交接手册第 N 版 .parallel-agent/交接手册/第N版-*.md，你是 T-X II 世，承接 T-X 身份`
- **回执待处理通知**：`读 .parallel-agent/信号/轮次状态/ 下的待处理状态文件（当前 job {ID}），可用 GET /watch/jobs 查看全部；处理完用 POST /watch/ack 标记`
- **超时/失败告警**：`读 .parallel-agent/信号/轮次状态/ 下的待处理状态文件（当前 job {ID}），有轨超时或失败，优先处理；可用 GET /watch/jobs 查看全部`

## 10. 一期手动触发工作流

```
用户对仲裁者说"把这个任务拆开跑"
   │
   ▼
[仲裁者 Skill 激活]
   ├─ 读契约/快照，先判奠基阶段（§4.3）：契约冻结？边界定义？骨架就位？
   ├─ 仍需奠基 → 仲裁者做轻量决策（写契约/定边界/出骨架），回到步骤 1
   ├─ 奠基已完成 → 按 §4 判据评估，输出决策建议（含收尾判据）
   ├─ 用户确认 → 写 转达/第1轮/T-{A,B,C}-v1.md（每轨一份，首部含收尾判据；可提前落盘）
   ├─ 记 since → fetch POST /new（各轨，只发待命话术）
   ├─ fetch POST /wait-ready（等 就绪/T-X.md；未就绪停止）
   ├─ 就绪后 fetch POST /dispatch（含轨号 + 轮次 + 版本 + 文件指针）
   └─ fetch POST /watch（提交 job，立即返回 job_id；此后结束回合）
   │
   ▼
[编排器插件 HTTP 收到 /dispatch]
   ├─ 解析信号（不含任务内容）
   ├─ CDP 切到目标轨 → 身份断言（任务名 = T-X）→ 注入话术 → 发送
   └─ 返回 {ok, sid, sent_at}；身份表持久化 sid → T-X
   │
   ▼
[各轨 Skill 并行激活]
   ├─ T-A 读 转达/第1轮/T-A-v1.md → 执行 → 写 回执/第1轮/T-A-v1.md（含自检字段）
   ├─ T-B 读 转达/第1轮/T-B-v1.md → 执行 → 写 回执/第1轮/T-B-v1.md
   └─ T-C 同上
   │
   ▼
[编排器插件后台 job（不占用 AI 回合）]
   ├─ 回执出现 + mtime 稳定 → 状态文件 状态=done、处理=pending
   ├─ 空闲探测（任务行图标 → status 二次确认）+ 输入框为空 → 注入待处理通知
   └─ 任一轨超时 → 状态=timeout、处理=pending → 立即注入告警话术
   │
   ▼
[仲裁者被唤醒（消费闭环）]
   ├─ 读 信号/轮次状态/第N轮-v{M}.json → 取一条待处理 → 读该轨回执
   ├─ 增量实检（只验该轨）→ 写 快照「已验」栏 → POST /watch/ack
   ├─ 剩余待处理非空 → 同一回合继续消费下一条
   ├─ 剩余为空且仍有轨未完成 → 结束回合，等下次唤醒
   └─ 全轨终态 → 整轮评估：自检报告 + 收回评估（§5.2 六维）
        ├─ 连续 2 轮 ≥2 条命中 → 写收回决策 → 路由收尾（§6）→ 必写交接手册

```

### 10.1 一期典型场景

1. 用户对仲裁者说"重构前端 + 后端 + 测试，拆开跑"
2. 仲裁者 Skill 引导 AI 评估 → 给出"拆 3 轨，理由：文件正交 + 收尾判据：..."
3. 用户："可以"
4. 仲裁者写转达单 → 调插件派发 → 提交 `/watch` job → 结束回合
5. 三轨并行跑，仲裁者不参与执行；每轨完成即入队，仲裁者空闲时被唤醒
6. 仲裁者逐条实检 + ack；全轨到齐后写快照 + 自检报告 + 收回评估 → 下一轮或收尾
7. 收回触发 → 仲裁者路由收尾（轻量亲做 / 用户开新会话承接重活）

### 10.2 异常路径

- 派发失败（CDP 找不到锚点）→ 插件返回 `{ok: false, err}` → 仲裁者告警用户
- 任一轨超时 → 状态文件立即置 `timeout` + `处理=pending` → 注入告警话术，仲裁者人工介入
- 身份断言失败（任务名 ≠ T-X）→ 插件 fail-stop，不做未校验的下发
- 注入通知时仲裁者忙 / 输入框有草稿 → 不注入，只更新状态文件，退避重试
- 注入通知重发 2 次仍无 ack → 降级 VS Code 气泡 + `alert.signal`，不再注入
- 弹窗出现 → 插件检测到 → 写 alert.signal，不自动点确认
- 会话自检告警 → 仲裁者写交接手册 → 用户开新会话承接（一期不自动派发第二任）

## 11. 状态自检与交接

> 详细指标见 `生命周期治理初稿.md` §6。本节固定一期落地。

### 11.1 不能直接获取上下文状态

Trae 不暴露：token 用量、上下文压缩次数、上下文剩余容量。可获取：`icube.chat.getSessionRunningStatus` → "WaitingInput" / "Running"（运行态，非健康度）、任务列表运行图标、发送按钮状态。

**健康度无官方 API，必须用间接指标。**

### 11.2 间接指标（仲裁者）

| 指标 | 阈值 |
|---|---|
| 错误率（最近 N 次工具调用失败次数 / N） | > 30% → 准备交接 |
| 决策迟疑度（输出决策建议的轮数变长） | > 3 轮 → 准备交接 |
| 重复输出（相同代码块/结论重复出现） | ≥ 3 次 → 立即交接 |
| 回执实检错误数 | 连续 2 轮上升 → 准备交接 |
| 自评失败（用户主动指出决策错误） | ≥ 2 次 → 立即交接 |

### 11.3 间接指标（分轨）

| 指标 | 阈值 |
|---|---|
| 工具调用错误率 | > 30% → 交接 |
| 身份断言失败（仲裁者核对该轨时任务名不匹配） | ≥ 2 次 → 立即交接 |
| 无新回执轮数 | ≥ 2 轮 → 交接 |
| 回执质量下降 | 连续 2 轮 → 交接 |
| 自评失败 | 立即交接 |

### 11.4 一期落地：AI 自评报告

一期不做自动状态采集，改为：

- **仲裁者每轮结束输出自检报告**（AI 自评，给用户参考）
- **分轨每轮回执附自检字段**（健康度自评）
- **用户在场决定是否交接**

仲裁者自检报告模板：

```
本轮自检（仲裁者）：
- 错误率：12%（最近 8 次工具调用 1 次失败）
- 决策迟疑度：1 轮
- 重复输出：0 次
- 回执实检错误：0
- 收回评估：剩余正交性 15%、无强依赖、无集成需求 → 不收回
- 健康度：良好 / 注意 / 警告
- 建议下一轮：继续 / 准备交接 / 立即交接
```

### 11.5 交接流程

1. 触发：自检告警 / 用户主动 / 阶段切换
2. 当前会话写交接手册（最新版）
3. 插件 `/new` 新会话 → 注入对应固定话术（§9.6）
4. 旧会话保留待命，不销毁（如需追溯）
5. 插件更新身份表（sid → 角色）
6. 新会话读手册 → 承接主控/分轨身份

**第二任仲裁者 / 第二任分轨**：新会话承接主控或分轨身份，旧会话保留至少 1 轮用于追溯。

## 12. 演进路径

> 三期对照见 `生命周期治理初稿.md` §7。

| 期 | 触发方式 | 决策方式 | 奠基 | 收回评估 | 第二任仲裁者 | 状态自检 |
|---|---|---|---|---|---|---|
| **一期**（当前） | 手动 | 仲裁者给建议 + 用户确认 | 用户手动 | 仲裁者每轮输出评估 | 用户开新会话手动 | AI 自评报告 |
| **二期** | 自动判定 + 建议式 | 仲裁者自动评估，需用户确认 | T-0 轨自动 | 自动采集指标 | 自动派发 | 插件采集指标 |
| **三期** | 自动 + override | 仲裁者自动拆，用户可拦截 | 仲裁者派 T-0 | 同 + 自动收回 | 同 + 智能路由 | 同 + 自动交接 |

**不要一期就做自动判定**。先把 Skill + 插件 + 文件信箱跑通，验证整套链路可靠，再加智能判定。

## 13. 风险登记

| 风险 | 等级 | 缓解 |
|---|---|---|
| 误发给错误轨道 | 高 | 发送前身份断言（任务名 + sid）；消息体只含文件指针；全程操作日志 |
| 仲裁者自指操作 | 高 | 控制脚本独立进程；断言目标窗口/任务；禁止在仲裁者自己的任务卡片上动作 |
| 插件 fallback 污染当前会话 | 高 | 插件不直接发会话消息（已证伪）；只走 CDP；只读命令可用 |
| 会话健康度退化未被察觉 | 高 | AI 每轮输出自检报告 + 收回评估；用户在场判断；阈值见 §11.2/§11.3 |
| 拆分节点判定错误（过早拆） | 中 | §4.3 奠基阶段判据；用户确认才开轨；一期用户手动奠基 |
| 收回判定错误（过晚收） | 中 | 拆分时预定收尾判据 + 每轮 6 维评估；连续 2 轮 ≥2 条命中即收 |
| 交接手册版本累积过载 | 中 | 只含结构性结论；按需读各回执；二期考虑归档机制 |
| Trae 更新导致锚点失效 | 中 | 稳定锚点优先（data-testid/语义类名）、外置配置、fail-stop；大版本后重跑探针 |
| 调试端口被本机滥用 | 中 | 非默认端口 9317、仅 127.0.0.1、用时才带参数 |
| 轨道卡死/弹窗永久挂起 | 中 | watch 超时 → 截图/DOM 诊断 → 告警升级，不盲点 |
| 通知注入打断用户会话或清空草稿 | 中 | 注入前判空（有草稿不注入）+ 注入后切回原会话；重发上限 2 次后降级气泡 |
| 逐轨唤醒切碎整轮评估 | 中 | 单轨只做增量实检，整轮评估留到全轨终态（见 v1.2.0 设计 §9.3） |
| 空转损耗（给待命轨造活） | 中 | 沿用收缩判据，连续两批活跃轨 < 2 即回归单线 |
| 锁屏后自动化失效 | 低（一期用户在场） | 文档注明前提；无人值守另案处理 |
| 扩展扫描缓存 stale | 低 | bump 版本号 + 全量重启 Trae，不全靠 Page.reload |
| 仲裁者 Skill 决策被覆盖 | 中 | 一期强制用户确认才开轨；二期建议式；三期保留 override |

## 15. 术语

- **仲裁者**：主控会话，落笔契约、派发任务、实检、裁决，产品口径问用户不代答
- **第二任仲裁者**：新会话承接主控权，仲裁者 Skill 同一份，旧会话保留待命
- **轨道（T-X）**：常驻任务会话，只在自己文件领地内作业，读转达、写回执
- **第二任分轨（T-X II 世）**：新会话承接某分轨身份，旧会话保留至少 1 轮
- **T-0 轨**：奠基先行轨，非常驻，完成后销毁或转做 T-A；二期实现
- **编排器**：自动化部件（A+B 合一插件），仲裁者的"手"，只做控制不做决策
- **文件信箱**：`.parallel-agent/` 下转达/回执/快照/手册/信号/交接手册的统称，系统唯一数据通道
- **身份断言**：发送前必读当前任务名/sid，断言 = 目标 T-X，否则 fail-stop
- **fail-stop**：找不到预期锚点或断言失败 → 立即停机告警，禁止未校验的下发
- **铁律**：控制面只传信号+固定话术+文件指针，绝不传任务内容
- **奠基阶段**（阶段 1）：拆分节点前的串行任务，仲裁者做轻量决策 + T-0 做重活
- **并行阶段**（阶段 2）：T-A/B/C/D 同时跑
- **收尾阶段**（阶段 3）：依赖收敛后的串行任务
- **拆分节点**：仲裁者判定可拆的时点（§4.3 奠基判据全满足）
- **收回节点**：仲裁者判定应收回的时点（§5 收回判据连续 2 轮 ≥2 条命中）
- **交接手册**：冷启动入口，关键节点写，只含结构性结论
- **自检报告**：AI 自评健康度，一期人工触发，分轨回执附自检字段

| 项 | 旧方案（探针前） | 本定稿 |
