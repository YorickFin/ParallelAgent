# ParallelAgent 第二期实现规划

> 状态：**已实施**（2026-10-26），代码与文档完成，待真机实测
> 前置：[ParallelAgent方案定稿.md](../../设计/ParallelAgent方案定稿.md)、[ParallelAgent生命周期治理初稿.md](../../设计/ParallelAgent生命周期治理初稿.md)、[ParallelAgent-v1.2.0设计文档.md](../v1.0.0+/ParallelAgent-v1.2.0设计文档.md)
> 版本：**v2.0.0+**
> 一句话：给 ParallelAgent 补上「入口分流 + 单轨治理 + 结果台账」，形成「一层分流、两层执行」的结构。

---

## 0. 文档定位

本文档是第二期的工程实现规划，覆盖：

- 为什么需要入口分流
- 分层关系怎么定（第一层分流、第二层单轨/多轨）
- 自动分流的判据、输出格式与升级/降级规则
- 单会话（单轨）的 L0-L3 流程与约束
- 小改动的结果落盘机制（单轨台账）
- 与现有三件套、文件信箱、编排器插件、CLI 的接口
- 实施步骤、验收标准、风险与待决项

**只新增能力，不改既有链路**：

- 不改多轨的转达/回执/快照/契约块格式
- 不改编排器插件的 CDP/HTTP 控制面
- 不改 v1.2.0 的 `/watch` job + 通知 + ack 闭环
- 不做自动开轨（L4 仍需用户确认）

## 1. 背景与问题

### 1.1 现状缺口

现有体系完整覆盖了「**多轨并行**」：

| 已有能力 | 载体 |
|---|---|
| 是否值得拆、拆几轨 | 仲裁者 Skill §4 四象限判据 |
| 奠基 → 并行 → 收尾 | 生命周期三阶段 |
| 轨道派发、就绪握手、回执闭环 | 编排器插件 + 转达/回执/就绪 |
| 收回评估、交接手册 | 仲裁者 Skill + 生命周期治理 |
| 多轨改动的溯源 | 转达单、回执、快照、契约块 |

但有两处空白：

1. **入口是手动的**：只有用户明确说“拆开跑/并行/分轨/开 N 轨”才进入仲裁者流程。绝大多数开发请求没有触发词，也没有任何分流判定。
2. **单会话没有约束**：一个会话里直接改代码，没有流程、没有记录、没有完成定义。多轨有回执可查，单轨改完就只剩聊天记录。

### 1.2 已确认口径（用户 2026-10-26 修正）

上一版设计提出“L0 直做允许零文档”，被用户否决：

> 允许零文档意味着小需求改动不可追溯，无数小需求改动都不能追溯回会导致项目崩塌。我认同小需求改动不需要走 PRD 流程，但是**结果需要落盘**。

因此第二期的硬口径是：

> **零计划文档 ≠ 零记录。计划可以省，结果必须留痕。**

- 小改动**不强制**写 PRD、spec、任务清单
- 但每次改动**必须有**可追溯的结果记录
- 记录只记“结果与证据”，不记“推理过程”

### 1.3 第二期要解决的问题

| 问题 | 对应设计 |
|---|---|
| 用户不说“拆开跑”时，谁来判定该走单轨还是多轨 | §5 自动分流 |
| 单会话的流程与约束是什么 | §6 单轨流程 L0-L3 |
| 小改动如何做到“不写计划但可追溯” | §7 单轨台账 |
| 分流与执行要不要分层 | §4 分层模型 |
| 分流判据与现有拆分判据如何不漂移 | §5.6 单一判据源 |

## 2. 结论先行

1. **要做分层，但只做“责任分层”，不做“运行时分层”。**
   - 第一层是**分流协议**（判据 + 输出格式 + 升级规则），不常驻、不建会话、不调插件。
   - 第二层是**执行模式**：单轨（L0-L3）或多轨（L4）。
   - 不新增独立的“分流 Skill”；最终仍是三个 Skill（arbiter / track / solo），单轨与仲裁者共用同一份分流判据，避免双写漂移。

2. **自动分流 = 自动判定 + 自动进入单轨；L4 只给建议，不自动开轨。**
   - 不需要用户先说“拆开跑”，入口 Skill 首轮就输出分流卡。
   - 判定为 L4 时，写任务卡与分流理由，等用户确认后再走现有 `/new` 流程。

3. **单轨不依赖编排器插件。**
   - L0-L3 全部在当前会话内完成，不调 HTTP、不建轨道、不写转达/回执。
   - 只有 L4 才进入现有三件套。

4. **台账是硬闸门。**
   - 代码改完 + 证据可核对 + 台账有条目，三者齐了才算完成。
   - 台账只追加、不修改；条目 ID 与 commit 关联。

5. **单轨不需要回执，台账条目承担回执角色。**
   - 单会话里执行者就是记录者，再写一份回执是重复劳动。
   - 但证据标准不降：仍要求文件路径 + 行号 / 命令 + 输出，不接受“已测试”。

## 3. 外部参照

第二期的分流与提问规则不是凭空设计，参照了 GitHub 上同类项目的做法：

| 项目 | 明确需求怎么走 | 不明确需求怎么走 | 可借鉴点 |
|---|---|---|---|
| [spec-kit](https://github.com/github/spec-kit) | `/specify` 直接写 spec；未定项用合理默认值并记入 Assumptions | `/clarify` **最多 5 问、一次一个**，每题给 2–5 个选项 + 推荐项 + “为什么重要”，答案逐条写回 spec | 提问配额、选项格式、答案回写 |
| [OpenSpec](https://github.com/Fission-AI/OpenSpec) | 直接 `/propose`，产出 proposal/specs/design/tasks | `/explore` 是纯思考模式：只读代码、提问、给选项，**不写码也不强制落文档** | “探路不产码”；明确/不明确双入口 |
| [BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD) | 小改动 `Change → Edit → Verify`；一会话 `Intent → Build` | 先走 brainstorm/forge/research 等探索技能，再 `bmad-spec` | **流程按规模分四档**；`bmad-spec` 只写契约，不负责帮用户想清楚 |
| [CCPM](https://github.com/automazeio/ccpm) | 已有 PRD 可直接拆 epic/task | 引导式头脑风暴（问题、用户、成功标准、约束、不做什么）后再写 PRD | “No Vibe Coding”，每行代码可回溯 |
| [Task Master](https://github.com/eyaltoledano/claude-task-master) | 可直接“帮我实现 X”，创建单个任务 | 建议先写 PRD，再解析成任务树 | PRD 只是推荐，不是强制 |
| [spec-kitty](https://github.com/spec-kitty/spec-kitty) | 走 `specify → plan → tasks → next → review → accept` | 同左，但明确说明对一次性小改动**属于过度设计** | 明确“什么时候不该用重流程” |

抽出的五条共识：

1. **入口先分流，不先建流程**：清晰度 × 规模决定路径。
2. **不明确先探路，探路不产码**：探索阶段只读、只问、只给选项。
3. **提问是稀缺资源**：必须有总配额、一次一个、给推荐、给影响。
4. **假设要显式化**：有合理默认值就不问，写进 Assumptions；只有影响范围/安全/验收且无默认值才问。
5. **允许跳过重流程，但不允许结果不可追溯**——这一点是本项目比外部项目更严格的地方，用台账补上。

## 4. 分层模型

### 4.1 三层视图

```
用户提出开发/修改请求
        │
        ▼
┌──────────────────────────────────────────────┐
│ Layer 1 · 入口分流（协议层，不常驻）            │
│ 输入：用户请求 + 仓库事实                       │
│ 输出：分流卡（模式 + 依据 + 必产文档 + 下一步）   │
│ 判据：清晰度 / 规模 / 风险 / 正交性              │
│ 不做：不写码、不建会话、不调插件、不落业务文件     │
└───────────────┬──────────────────────────────┘
                │
      ┌─────────┴─────────┐
      ▼                   ▼
┌───────────────┐   ┌───────────────────────────┐
│ Layer 2A 单轨  │   │ Layer 2B 多轨               │
│ L0 / L1 / L2 / L3 │   │ L4：仲裁者 + 轨道 T-A/B/C   │
│ 当前会话        │   │ 现有三件套 + 文件信箱        │
│ 不依赖插件      │   │ 依赖编排器插件               │
│ 台账为结果凭证  │   │ 回执/快照为结果凭证           │
└───────────────┘   └───────────────────────────┘
```

### 4.2 为什么这样分层

| 方案 | 分流放在哪 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| **A. 独立入口 Skill** `parallelagent-intake` | 新增第三个入口 Skill | 入口职责最清晰，所有请求先过它 | 多一个 Skill；与 solo/arbiter 存在激活竞争；每次都要二次转交 | 备选 |
| **B. 共享分流 reference + 双入口**（本方案） | `shared/references/分流.md`，solo 与 arbiter 在 §0 共同调用 | 不新增 Skill；不为常见路径增加转交；判据单一源 | 两个入口都要执行 §0，靠描述互斥保证不抢 | **推荐** |
| **C. 仲裁者升级为总入口** | 仲裁者 Skill 内做分流 + 多轨 | 只改一个 Skill | 违背仲裁者“不解析任务内容”的边界；小需求也要加载多轨知识，上下文膨胀 | 否决 |

**为什么推荐 B**：

- 单轨是绝大多数请求的路径，不该为它增加一次“从 intake 转交到 solo”的额外步骤。
- 仲裁者本来就有 §4 拆分判据；把同一份判据抽到 `分流.md`，两个入口引用即可，不复制阈值。
- 项目铁律是“Skill 极薄”，三个 Skill（arbiter / track / solo）已经够用。
- 如果实践中仍出现“入口职责不清”，再把 Layer 1 抽成独立 Skill；**协议不变，只换载体**。

### 4.3 层级契约

| 角色 | 权力 | 限制 |
|---|---|---|
| **Layer 1 分流** | 决定 L0-L4；输出分流卡；可直接跳级（L0→L3） | 必须写依据；不得无证据跳级；不执行代码 |
| **Layer 2A 单轨** | 执行 L0-L3；可向上升级 | 只能凭新证据升级；不得静默降级；不得改用户已确认的口径 |
| **Layer 2B 多轨** | 承接 L4；按现有仲裁流程执行 | 不改分流判据；用户未确认不得开轨 |
| **用户** | 最高 override：`按 L0 做` / `别问了` / `直接拆` / `停` | — |
| **插件** | 只执行控制信号 | 不参与分流判定、不解析任务内容 |

### 4.4 与现有三阶段生命周期的映射

第二期**不新增阶段**，只是把已有阶段补齐：

| 现有阶段 | 第二期落位 |
|---|---|
| 阶段 1 奠基串行 | **单轨 L2/L3** 就是奠基的约束层；不再只靠用户手动 |
| 阶段 2 并行多轨 | **L4**，现有仲裁者 + 轨道流程不变 |
| 阶段 3 收尾串行 | 轻量收尾 → 单轨 L0/L3；重活 → 第二任仲裁者（现有路由不变） |

换句话说：**单轨不是多轨的替代品，而是阶段 1 的正式入口**。

## 5. 自动分流设计

### 5.1 判定维度

#### 5.1.1 清晰度（5 项检查）

| # | 检查项 | 判定 |
|---|---|---|
| 1 | 目标能否用一句话说清要达成什么 | 否 → 不明确 |
| 2 | 范围与非目标是否明确 | 否 → 不明确 |
| 3 | 输入输出、数据结构、接口形态是否明确 | 否 → 不明确（影响实现时） |
| 4 | 关键异常/边界路径是否明确 | 否 → 不明确（影响验收时） |
| 5 | 能否写出可执行的验收命令或可观察结果 | 否 → 不明确 |

**规则**：

- 不是 5 项全“否”才算不明确；只要有一项影响范围、验收或安全，就判不明确。
- 不影响实现和验收的空白，**不问**，写进 Assumptions。
- 清晰度判定必须说明依据，不能只给结论。

#### 5.1.2 规模

| 档位 | 判据 |
|---|---|
| 小 | ≤ 2 个文件且 ≤ 50 行；无公开接口/数据结构/配置变更 |
| 中 | 3–10 个文件，或 50–300 行 |
| 大 | > 10 个文件，或 > 300 行，或跨模块/跨层 |

#### 5.1.3 风险

| 档位 | 判据 |
|---|---|
| 高 | 数据迁移/删除、认证授权、公开 API、生产配置、不可逆操作、跨项目影响 |
| 中 | 依赖升级、构建配置、性能敏感路径 |
| 低 | 文案、样式、局部逻辑、测试补充 |

#### 5.1.4 正交性（仅大任务）

**直接复用仲裁者 §4.1 的四象限判据，不另立阈值**：

- 文件重叠度 < 20%
- 子任务可独立验收
- 总量 > 500 行
- 等待时间占比 > 30%（可选加权）

只有同时满足「强拆」条件，才允许判 L4。

### 5.2 分流矩阵

| 清晰度 | 规模 | 风险 | 模式 | 计划文档 | 结果记录 | 执行位置 |
|---|---|---|---|---|---|---|
| 明确 | 小 | 低 | **L0 直做** | 无 | 台账（简记/全记） | 当前会话 |
| 明确 | 中 | 低 | **L0 直做** | 无 | 台账（全记） | 当前会话 |
| 明确 | 中/大 | 中/高 | **L3 立规** | 任务卡 | 台账 | 当前会话 |
| 不明确 | 小 | 低/中 | **L1 问清** | 无 | 台账（含问答） | 当前会话 |
| 不明确 | 中/大 | 任意 | **L2 探路 → L3** | 任务卡 | 台账 | 当前会话 |
| 明确/不明确 | 大 | 任意 | **L4 拆轨**（仅当强拆判据满足） | 任务卡 + 分流卡 | 回执/快照 | 仲裁者 + 轨道 |

补充规则：

- **明确 + 大 + 不可正交拆分** → L3（单轨立规），不强行拆。
- **不明确 + 大** → 先 L2 探路；方案选定后若满足强拆条件，再升 L4，否则 L3。
- **L4 只有在用户确认后才真正开轨**；未确认前只产出任务卡与建议。
- 任何模式命中 §6.8 的 fail-stop 条件，立即停并升级，不带着猜测继续。

### 5.3 分流卡格式

分流卡是 Layer 1 的唯一输出，默认放在对话里；L2/L3/L4 另写任务卡，L4 的任务卡额外包含建议拆轨与分流理由。

```markdown
分流卡 · 2026-10-26 14:32 · <slug>
- 模式：L1 问清
- 依据：目标明确；验收方式缺失；预估 2 文件 / 30 行；低风险
- 未知项：① 失败提示是否需要可配置 ② 是否记录尝试次数
- 必产：单轨台账（含问答）；无需任务卡
- 下一步：连问 ≤3 个问题 → 直接执行 → 写台账
- 可 override：回复“直接做 / 别问了 / 拆开跑”
```

L4 版本：

```markdown
分流卡 · 2026-10-26 15:10 · <slug>
- 模式：L4 拆轨
- 依据：文件边界正交（重叠 < 10%）+ 总量约 800 行 + 各轨可独立验收
- 建议：3 轨（T-A 前端 / T-B 后端 / T-C 测试）
- 必产：任务卡 + 分流理由；由仲裁者写契约与转达单
- 下一步：用户确认后，仲裁者按现有流程 /new → /wait-ready → /dispatch
- 风险：T-B 改 API 后 T-A 需同步，已在任务卡标注依赖
```

### 5.4 “自动”的边界

**自动的含义**：

- 用户不需要先喊“拆开跑”；入口 Skill 首轮就完成判定并输出分流卡。
- 执行者：普通请求由 `parallelagent-solo` 在首轮执行分流；明确带拆轨词的请求由 `parallelagent-arbiter` 执行同一份分流判据。
- L0-L3 由 AI 直接进入对应流程，不额外等用户批准（除非触发提问/fail-stop）。
- L4 自动完成判定与任务卡，但**开轨仍需用户确认**——这是现有铁律，不在第二期放开。

**不自动的含义**：

- 不自动创建轨道会话。
- 不自动调用编排器 HTTP。
- 不自动提交代码、不自动推送。
- 不做“机器学习分类器”或“插件规则引擎”；分流是 AI 按固定判据表的判定，不是黑盒模型。

**用户 override 优先**：

| 用户说 | 结果 |
|---|---|
| “直接做 / 别问了” | 强制 L0；未知项全部转 Assumptions/Deferred |
| “先问清楚” | 强制 L1/L2 |
| “拆开跑 / 并行 / 开 N 轨” | 直接进 L4 评估 |
| “按 L3 做” | 强制立规，不拆 |

### 5.5 升级与降级

| 从 | 到 | 触发 | 必须记录 |
|---|---|---|---|
| L0 | L1 | 读代码后发现影响验收的未知 | 台账/任务卡 |
| L0/L1 | L2 | 规模或风险上升；涉及选型/架构 | 任务卡 |
| L1/L2 | L3 | 方案选定，需要契约与验收条件 | 任务卡 |
| L3 | L4 | 满足强拆判据 + 用户同意 | 分流卡 |
| L4 | L3 | 用户拒绝拆 / 可用轨不足 / 依赖过强 | 分流卡 |
| 任意 | fail-stop | §6.8 任一命中 | 台账/任务卡 |

约束：

- **允许直接跳到目标层级**（例如 L0 发现是 L3），但必须写清证据，不得无理由跳级。
- **不允许静默降级**：从 L3 降回 L0 必须说明为什么风险已消除。
- 一次只处理一次升级/降级，不连环改判；用户 override 除外。

### 5.6 判据单一源

- 新增 `shared/references/分流.md`，存放：清晰度检查、规模/风险档位、分流矩阵、分流卡模板、升级/降级规则。
- 仲裁者 Skill §4 的四象限判据**引用同一份文件**，不复制阈值。
- 如果未来要调整“强拆”阈值，只改 `分流.md` 一处；solo 与 arbiter 同时生效。
- 这与 `协议.md` 的定位一致：**共享 reference 是唯一源，Skill 只引用不复述**。

## 6. 单轨流程设计

### 6.1 L0 直做（明确 + 小/中 + 低风险）

**适用**：文案、样式、局部逻辑、单文件小修、测试补充。

**流程**：

1. 读相关文件，确认改动边界（不改无关文件）。
2. 写一句意图与验收口径（对话里说明即可，不落任务卡）。
3. 执行改动。
4. 自检：跑相关命令 / 核对 diff。
5. 写台账条目（简记或全记，见 §7.3）。
6. 汇报：改了什么、证据是什么、台账 ID 是什么。

**不做**：

- 不写 PRD / spec / 任务清单
- 不建轨道、不调插件
- 不写交接手册

### 6.2 L1 问清（不明确 + 小）

**适用**：需求方向清楚，但有一两个影响验收的空缺点。

**流程**：

1. 先读代码/配置，排除“代码里能查到”的问题。
2. 生成候选问题，按影响排序，取 ≤3 个。
3. 一次只问一个，按 §6.6 格式。
4. 每个答案立即写入台账草稿（或对话中的临时记录，最终并入台账）。
5. 问完（或用户说停）后直接执行。
6. 写台账全记条目，含问答。

**上限**：≤3 问。超过 3 个仍未解决 → 升级 L2，不硬问。

### 6.3 L2 探路（不明确 + 中/大）

**适用**：需求概念清楚，但方案、边界或可行性未定。

**流程**：

1. 只读：代码、依赖、现有实现、相关文档。
2. 给 2–3 个可选方案，说明代价、风险、放弃的理由。
3. **不写码**；除非用户明确说“先做个 spike”，否则不产生实现改动。
4. 产出任务卡（见 §6.7.1），记录：目标、非目标、未知项、假设、候选方案、选定方案、验收条件。
5. 用户确认方案后 → L3；若发现满足强拆条件 → L4。

**硬约束**：探路阶段最多只改任务卡/台账，不改业务代码。

### 6.4 L3 立规（明确 + 中/大 + 中/高风险，或 L2 收敛后）

**适用**：改动大、风险高、需要先定契约再动手。

**流程**：

1. 写任务卡：目标、非目标、文件领地、接口/数据约束、验收条件、回滚方式。
2. 用户确认任务卡（至少确认验收条件与非目标）。
3. 按任务卡执行，不越界。
4. 每完成一个可验证单元，写一次台账（允许批量，但不允许最后补记）。
5. 全部验收条件逐条核对，写最终结论。
6. 若执行中发现强拆机会且用户同意 → L4。

**与多轨的关系**：

- L3 的任务卡就是 L4 任务卡的同一份格式；升级时不需要重写。
- 任务卡里的“文件领地”可直接作为仲裁者划分轨道的输入。

### 6.5 L4 拆轨（移交现有体系）

**流程**：

1. Layer 1 输出分流卡 + 任务卡（含建议拆轨与文件领地）。
2. 用户确认“拆”。
3. 仲裁者读取任务卡，按其 §4.3 奠基判据复核；缺口补齐后进入现有流程。
4. 后续完全走 v1.2.0：写转达单 → `/new` → `/wait-ready` → `/dispatch` → `/watch` → 回执 → 实检 → 收回。
5. 单轨台账不记录多轨执行细节；多轨用回执/快照。若收回后由单轨收尾，收尾部分重新进入 L0/L3，并写台账。

**硬约束**：单轨在 L4 只写任务卡与分流卡，不执行任何业务改动。

### 6.6 提问规范

借鉴 spec-kit 的 `/clarify`，并做本项目的简化：

| 规则 | 内容 |
|---|---|
| 总配额 | L1 ≤ 3 问；L2/L3 ≤ 5 问；一次会话累计不超过 5 问 |
| 节奏 | **一次只问一个**，不一次性列一串 |
| 每题结构 | `问题` + `为什么重要（一句）` + `推荐项及理由` + `2–5 个互斥选项` 或 `≤5 词短答` |
| 推荐 | 必须给出推荐项；推荐要说明依据（项目约束、风险、常见做法） |
| 禁止问 | 代码/配置里能查到的；纯风格偏好；纯技术选型（除非阻塞功能或验收） |
| 优先级 | 范围 > 安全/数据 > 用户体验 > 技术细节 |
| 答案处理 | 每个答案立即写回任务卡/台账；不留在对话里 |
| 提前停止 | 关键歧义已解决，或用户说“停/别问了/直接做” |
| 超额处理 | 超过配额仍未决 → 写入 Deferred，标注风险，交给用户决定，不硬问 |

**题目格式示例**：

```markdown
**问题：** 登录失败提示里是否需要显示剩余尝试次数？
（为什么重要：这决定要不要改后端返回结构，影响验收用例。）

**推荐：** 选项 B —— 只在前端提示，不改接口，风险最小。

| 选项 | 说明 |
|---|---|
| A | 后端返回剩余次数，前端展示 |
| B | 前端只提示“还有机会”，不改接口 |
| C | 不提示次数，只提示失败 |
| 短答 | 用 ≤5 词给出你的答案 |

回复选项字母即可；也可以说“推荐”或直接给短答。
```

### 6.7 假设与未决项

#### 6.7.1 任务卡模板

```markdown
# <slug> 任务卡

- 分流：L2 / L3 / L4
- 创建：2026-10-26T14:32+08:00
- 原始需求（用户原话摘要）：
- 目标：
- 非目标：
- 未知项：
- 假设（Assumptions）：
- 候选方案 / 选定方案：
- 文件领地：
- 验收条件（可执行/可观察）：
- 证据位置：
- 未决项（Deferred）：
- 升级/降级记录：
- 回滚方式：
```

L4 追加：

```markdown
- 建议拆轨：
- 各轨文件领地：
- 收尾判据：
```

#### 6.7.2 假设规则

- 有合理默认值 → 不問，写入 `假设`，并在最终汇报中复述一次。
- 假设影响验收/安全/范围 → 必须问，不能猜。
- 假设被后续证据推翻 → 更新任务卡，不静默改代码。

#### 6.7.3 未决项规则

- 超过提问配额仍未决的，写入 `Deferred`，标注“为什么现在不能决”和“后续触发条件”。
- 未决项不能阻塞执行时，按保守默认值执行并标注。
- 未决项阻塞验收时，fail-stop，不执行。

### 6.8 fail-stop 触发条件

以下任一命中，**立即停止执行**，不得带着猜测继续：

1. 验收条件写不出（无法验证）。
2. 需要改动的文件超出任务卡/意图声明范围。
3. 涉及数据迁移/删除、认证授权、公开 API、生产配置，且用户未给明确口径。
4. 有两种合理实现，后果不同，且没有可辩护的默认值。
5. 无法写台账（不知道改了哪些文件 / 没有可核对证据）。
6. 用户明确说“停”。

处理方式：

- 在提问配额内 → 问清楚再继续。
- 配额用尽 → 升级 L2/L3，或交给用户决策。
- **禁止**“先改完再问”“先猜一个再说”。

### 6.9 完成定义（Definition of Done）

单轨任务只有同时满足以下条件，才允许向用户汇报“完成”：

1. 代码/文档改动已完成，且未越界。
2. 验收证据可核对（命令输出 / 文件行号 / diff）。
3. 台账条目已写入，字段完整。
4. 台账条目与 commit 关联（按 §14 Q2 的口径）。
5. 未决项已记录，或已解决。
6. L3 额外要求：任务卡的验收条件逐条满足。
7. L4 不适用本节，按现有回执/快照口径。

**缺任何一项，都不得说“完成”**；只能说“已改完，待补记录/待验证”。

### 6.10 会话退化与冷启动

单轨同样会遇到上下文膨胀、错误率上升。沿用现有自检思路，但去掉多轨的六维收回评估：

| 指标 | 阈值 | 动作 |
|---|---|---|
| 工具调用错误率 | > 30% | 准备新会话 |
| 重复输出 | ≥ 3 次 | 立即新会话 |
| 用户连续指出错误 | ≥ 2 次 | 立即新会话 |
| 无法说清当前改动范围 | 出现即触发 | 立即新会话 |

冷启动方式：

1. 当前会话写/更新任务卡（若还没有，至少写一份“当前状态 + 下一步”）。
2. 汇总最近台账条目 ID。
3. 新会话首条消息：`读 .parallel-agent/单轨/任务卡/<slug>.md 与最近台账，继续 <slug>`。
4. 不写交接手册——任务卡 + 台账就是单轨的冷启动入口。

## 7. 单轨台账

### 7.1 定位

| 项 | 结论 |
|---|---|
| 是什么 | **结果记录**：谁要的、改了什么、怎么证明、结论如何、怎么回滚 |
| 不是什么 | 不是过程日志、不是推理记录、不是 PRD、不是聊天记录备份 |
| 与 git 的分工 | git 记录 diff；台账记录 **意图 + 验收 + 结论**，即 git 覆盖不了的部分 |
| 与多轨回执的分工 | 单轨台账只覆盖 L0-L3；L4 用现有回执/快照，不双写 |
| 写入方式 | 只追加；不修改历史；记错追加“更正”条目引用原 ID |

### 7.2 目录与命名

```
.parallel-agent/
  单轨/
    台账/
      2026-10.md              # 按月一个文件（Q1=B 已确认）
    任务卡/
      <slug>.md               # L2/L3/L4 才有
    证据/
      S-20261026-004/
        test-output.txt       # 可选：命令输出、截图说明
```

- 台账 ID：`S-YYYYMMDD-NNN`，按月顺序递增。
- 台账文件、任务卡入 git；证据以文本为主，截图等二进制按项目仓库规则处理。
- `.parallel-agent/信号/` 仍只由插件使用，单轨不写信号文件。

### 7.3 条目模板

#### 7.3.1 简记（非行为改动）

适用：注释、文案、格式、纯测试补充、依赖小版本。

```markdown
## S-20261026-003 · 2026-10-26 14:32 · L0
- 需求：修正登录页文案错别字（用户原话：“把‘登入’改成‘登录’”）
- 改动：src/ui/LoginForm.tsx（+2/-2），commit a1b2c3d
- 证据：diff 已核对；无运行时行为变化
- 结论：通过
```

#### 7.3.2 全记（行为/接口/数据/配置变更）

适用：任何会改变外部可观察行为的改动。

```markdown
## S-20261026-004 · 2026-10-26 15:10 · L1
- 需求（原话）：登录失败要提示剩余尝试次数（“至少告诉我还剩几次”）
- 目标 / 非目标：只改前端提示；不改后端锁定策略
- 问答：Q1 是否需要可配置 → A 先硬编码 5 次；Q2 是否记录尝试 → A 不记录
- 改动：src/auth/login.ts、src/ui/LoginForm.tsx（+42/-8），commit d4e5f6a
- 证据：`pnpm test auth` → 12 passed；空密码用例返回 400
- 结论：通过
- 未决 / 风险：锁定阈值 5 次未与产品确认
- 回滚：git revert d4e5f6a
```

### 7.4 ID 与 commit 关联（Q2=D 混合口径）

- 每条台账必须有唯一 ID。
- **行为变更**（接口/数据/配置/可观察逻辑）：与代码同一个 commit，台账条目必须写 commit hash。
- **非行为变更**（文案/注释/格式/测试补充）：允许 `未提交` 条目，但会话结束前必须回填 commit hash；确实无法提交时标注 `未提交（原因）`。
- 批次提交：一个 commit 可以对应多条台账；台账更新必须包含在同一 commit 中。
- 未提交条目：下一次单轨会话启动读取时优先处理（补提交或说明原因）。
- commit message 建议格式：`<type>: <subject> [S-YYYYMMDD-NNN]`。
- 一条台账只能对应一个 commit（或未提交状态）。

### 7.5 证据规则

**只接受可核对证据**：

- 命令 + 退出码/输出摘要（如 `pnpm test auth` → 12 passed）
- 文件路径 + 行号
- diff 片段（用于纯文案/格式改动）
- 截图/录屏（引用 `证据/<ID>/` 下的文件）

**不接受**：

- “已测试”“应该没问题”“本地验证过了”这类自述
- 无法复现的口头结论
- 与改动无关的旧测试结果

### 7.6 会话启动读取

单轨 Skill 启动时：

1. 读最近 10 条台账（或当月全部）。
2. 检查是否有同文件冲突、未决项、未回填 commit。
3. 若有同文件未决项，先向用户提示，再决定是否继续。

这使台账不仅是审计材料，也是**下一个会话的冷启动入口**——比聊天记录可靠。

### 7.7 与多轨回执的关系

| 场景 | 记录载体 |
|---|---|
| L0-L3 单轨改动 | 单轨台账 |
| L4 多轨执行 | 转达单 + 回执 + 快照（现有） |
| L4 收回后由单轨收尾 | 收尾部分写单轨台账，并在条目中引用 `收回决策` 与相关回执 |
| 第二任仲裁者交接 | 交接手册（现有），不写单轨台账 |

## 9. 与现有部件的接口

### 9.1 Skill 激活与互斥

| Skill | 激活 | 不激活 |
|---|---|---|
| `parallelagent-solo` | 任何需要改代码/文档/配置的开发请求，且用户未明确说“拆开跑/并行/分轨/开 N 轨” | 明确要求拆轨；纯问答/研究/查资料 |
| `parallelagent-arbiter` | 用户明确说“拆开跑/并行/分轨/开 N 轨”；或单轨判定 L4 后的转交 | 小改动、单文件修改、明确说“别拆” |
| `parallelagent-track` | 由插件注入“读手册，你是 T-X，待命” | 用户直接对话、单轨任务 |

**互斥规则写进 description**：

- solo：`任何未明确要求拆开跑的开发请求；先执行分流，L4 时转交仲裁者`
- arbiter：`仅当用户明确要求拆开跑/并行/分轨，或单轨判定 L4 后转交；不处理小改动`
- track：`仅由编排器注入启动话术时激活`

### 9.2 共享 reference

- `分流.md`：solo 与 arbiter 的共同 §0，**唯一判据源**。
- `台账.md`：solo 专用；arbiter 不读台账（多轨用回执/快照）。
- `协议.md`：多轨协议不变；在目录结构一节补一行「单轨目录」指针，避免两套目录文档分裂。

### 9.3 编排器插件

**第二期不改插件运行时**：

- L0-L3 不调 HTTP、不建轨道、不依赖 CDP。
- 插件启动时创建 `.parallel-agent/` 目录的逻辑可以**可选**追加 `单轨/台账`、`单轨/任务卡`，但单轨 Skill 必须能在插件未启动时自行创建目录。
- 插件继续只做执行，不参与分流判定。

### 9.4 CLI

- `packages/cli/assets/skills/` 从 2 个 Skill 扩到 3 个（新增 `parallelagent-solo`）。
- `init` 铺 Skill 时保持幂等，已存在则覆盖。
- `doctor` 增加台账校验（Q3=B 已确认）：只告警，不阻断，不影响退出码。
- `uninit` 需要删除新增的 solo Skill 目录。
- 版本号：项目整体 `v2.0.0`；扩展版本按实际改动 bump（若插件不改，扩展版本可不动）。

## 11. 关键设计约束

1. **零计划文档 ≠ 零记录**：L0/L1 可以不建任务卡，但必须有台账条目。
2. **单轨不依赖插件**：停掉编排器，L0-L3 仍可完整执行。
3. **分流只判定，不执行**：Layer 1 不写业务代码、不建会话、不调 HTTP。
4. **控制面不传任务内容**：多轨铁律不变；单轨不产生控制信号。
5. **判据单一源**：清晰度/规模/风险/正交性只在 `分流.md` 定义；仲裁者引用，不复制。
6. **fail-stop**：验收写不出、改动越界、高风险无口径、无法记录 → 停，不猜。
7. **台账只追加**：不修改历史；更正用新条目引用原 ID。
8. **用户 override 最高**：`直接做/别问了/拆开跑/停` 优先于任何自动判定。
9. **不自动开轨**：L4 必须用户确认；这是现有铁律，不在第二期放开。
10. **不改多轨协议**：转达/回执/快照/契约块/`/watch` 语义全部保持 v1.2.0。
11. **证据不接受自述**：只认命令、行号、diff、可打开的截图。
12. **单轨不写交接手册**：任务卡 + 台账就是冷启动入口；不复制多轨的交接成本。

## 12. 验证方式与验收标准

### 12.1 分流矩阵用例

| # | 输入 | 期望模式 | 关键断言 |
|---|---|---|---|
| 1 | “把登录页的‘登入’改成‘登录’” | L0 | 无任务卡；台账简记；不调插件 |
| 2 | “登录失败要提示剩余次数” | L1 | ≤3 问；一次一个；有推荐；答案入台账 |
| 3 | “给项目加一个可插拔的权限系统，我还没想好模型” | L2 → L3/L4 | L2 不写业务码；产出任务卡 |
| 4 | “重构前端 + 后端 + 测试，拆开跑” | L4 | 分流卡 + 任务卡；用户确认后才开轨 |
| 5 | “重构整个项目的日志层” | L2/L3 | 不因为没说“拆开跑”就跳过分流；不强行拆 |
| 6 | L0 改到一半发现要改 8 个文件 | 升级 L2/L3 | 停止并写升级记录；不得继续按 L0 硬改 |

### 12.2 验收标准

1. 明确小需求：无任务卡，台账有简记/全记条目，包含需求、改动、证据、结论。
2. 不明确小需求：提问 ≤3 个，一次一个，有推荐和影响说明；答案写入台账；不问代码可查项。
3. 不明确大需求：L2 阶段不改业务代码；任务卡包含目标/非目标/未知/假设/验收。
4. 明确大且正交：输出 L4 分流卡 + 任务卡；**未确认前不调用 `/new`**。
5. 越界或无法验收：fail-stop；不产生未校验的改动。
6. 台账：ID 唯一、只追加、字段完整；下一次会话能据此恢复上下文。
7. 无台账不得汇报完成：抽查 3 个场景，缺少台账时必须报“待补记录”。
8. 单轨独立：停掉插件后，L0-L3 全流程仍可完成。
9. 多轨回归：v1.2.0 的派发、就绪、watch、ack、收回流程不受影响。
10. CLI：`init` 安装 3 个 Skill；`uninit` 清理干净；重复执行幂等。
11. Skill 互斥：说“拆开跑”时 arbiter 激活、solo 不抢；普通小改动时 solo 激活、arbiter 不抢。

## 13. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 分流误判 | 小改动走了重流程，或大改动直接动手 | 输出依据 + 用户 override + 允许升级/降级；不无证据跳级 |
| 提问过多 | 用户放弃流程 | 配额（L1≤3、L2/L3≤5）+ 一次一个 + 必须给推荐 |
| 台账摩擦导致漏记 | 追溯链断裂 | 完成定义硬闸门 + 简记模式 + fail-stop |
| 台账膨胀 | 检索变慢、diff 噪音 | §14 Q1 粒度选择；按月分文件 |
| 台账与 commit 脱节 | 无法定位改动 | §14 Q2 口径；未提交条目必须标注并回填 |
| Skill 激活冲突 | 该走单轨却进了仲裁者，或反之 | description 互斥 + 实测用例 11；必要时把 Layer 1 抽成独立 Skill |
| 单轨与多轨双写 | 同一改动两份记录、口径不一 | 单轨台账只覆盖 L0-L3；L4 用回执/快照 |
| 过度文档化 | 小改动也写任务卡 | L0/L1 禁止建任务卡；只有 L2+ 才写 |
| 证据造假/自述 | 记录不可信 | 只认命令/行号/diff/截图；下一次会话可复核 |
| 自动分流被误解为自动开轨 | 未经确认就建会话 | 文档与话术明确：L4 只给建议；插件不参与判定 |
| 单轨会话丢失 | 任务无法恢复 | 任务卡 + 台账作为冷启动入口；关键节点写任务卡 |
| 判据双写漂移 | solo 与 arbiter 判定不一致 | 单一源 `分流.md`；仲裁者只引用 |

## 14. 已确认口径（2026-10-26）

以下口径已于 2026-10-26 由用户确认，作为第二期实施依据。

| 编号 | 问题 | 选定 | 生效位置 |
|---|---|---|---|
| Q1 | 台账文件粒度 | **B 按月分文件** | §7.2 |
| Q2 | 台账与代码提交关系 | **D 混合** | §7.4 |
| Q3 | doctor 是否增加台账校验 | **B 只告警** | §9.4 / §10 C2 |

### Q1 台账文件粒度（选定 B）

| 选项 | 形态 | 结论 |
|---|---|---|
| A | 单文件 `单轨/台账.md` | 未选 |
| **B** | 按月 `单轨/台账/YYYY-MM.md` | **选定** |
| C | 每条一文件 `单轨/台账/S-YYYYMMDD-NNN.md` | 未选 |

**落地规则**：

- 当月条目写入 `单轨/台账/YYYY-MM.md`；跨月新建下月文件，不在旧文件续写。
- ID 仍按 `S-YYYYMMDD-NNN` 全局唯一，NNN 在月内递增。
- 会话启动读取「当月文件」以及「上月文件中未决/未提交的条目」。

### Q2 台账与代码提交关系（选定 D）

| 选项 | 规则 | 结论 |
|---|---|---|
| A | 每次变更与代码同一个 commit | 仅行为变更采用 |
| B | 允许“未提交”条目，下一次提交时回填 hash | 仅非行为变更采用 |
| C | 按批次统一提交，批次结束时补台账 | 未选 |
| **D** | 混合：行为变更走 A，非行为变更走 B | **选定** |

**落地规则**：

1. **行为变更**（接口/数据/配置/可观察逻辑）：与代码同一个 commit；台账条目必须写 commit hash。
2. **非行为变更**（文案/注释/格式/测试补充）：允许 `未提交` 条目，但会话结束前必须回填 commit hash；确实无法提交时标注 `未提交（原因）`。
3. **批次提交**：一个 commit 可对应多条台账；台账更新必须包含在同一 commit 中。
4. **未提交条目**：下一次单轨会话启动读取时优先处理（补提交或说明原因）。

### Q3 doctor 台账校验（选定 B）

| 选项 | 内容 | 结论 |
|---|---|---|
| A | 不做 | 未选 |
| **B** | 只告警：台账目录缺失、最近条目字段不全、存在未回填 commit | **选定** |
| C | 阻断：校验失败则 doctor 退出码非 0 | 未选 |

**落地规则**：

- 校验项：台账目录存在；最近 N 条字段完整（需求/改动/证据/结论）；`未提交` 条目是否有回填提醒。
- 校验失败只输出警告，不阻断，不改变 doctor 退出码（全绿仍为 0）。

## 16. 术语补充

| 术语 | 含义 |
|---|---|
| 入口分流 | Layer 1 的职责：按清晰度/规模/风险/正交性判定执行模式 |
| 分流卡 | 分流判定的固定输出：模式、依据、未知项、必产文档、下一步 |
| 单轨 | 单会话执行模式，覆盖 L0-L3，不依赖编排器 |
| 多轨 | 现有仲裁者 + 轨道模式，对应 L4 |
| 任务卡 | L2/L3/L4 的计划与约束文件；L4 时作为移交仲裁者的输入 |
| 单轨台账 | 单轨改动的结果记录，只追加，含需求/改动/证据/结论 |
| 简记 / 全记 | 台账的两种深度；按是否改变外部可观察行为区分 |
| 升级 / 降级 | 分流模式的变更；必须写触发证据，不得静默降级 |
| 证据 | 可核对的命令输出、文件行号、diff、截图；不接受自述 |
| 完成定义 | 改完 + 证据 + 台账 + 未决项记录，四者齐备才算完成 |
