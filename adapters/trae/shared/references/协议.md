# ParallelAgent 文件信箱协议

> 本文件是多轨文件信箱的共享协议 reference，仲裁者 / 轨道 / 单轨 Skill 共同引用。
> 入口分流见 `分流.md`，单轨台账见 `台账.md`；多轨协议修改只改本文件。

---

## 1. 目录结构

```
.parallel-agent/
  轨道启动手册.md            # 新会话首条消息永远指向它
  转达/第N轮/T-X-v{M}.md     # 每轮一目录、每轨一文件（首部含收尾判据；同轮可多次转达，M 从 1 递增）
  回执/第N轮/T-X-v{M}.md     # 各轨完成后自写（含自检字段，与转达对称，版本号对齐）
  就绪/T-X.md                # 轨道完成启动、进入待命时自写（开轨握手信号，无轮次无版本）
  快照.md                    # 仲裁者每批后回写：轨/状态/欠账/收回决策
  契约块.md                  # 嵌代码注释形式的最终结论
  交接手册/
    第1版-开轨前.md
    第2版-收回决策.md
    第3版-第二任仲裁者启动.md
  单轨/
    台账/YYYY-MM.md          # 单轨 L0-L3 结果记录（按月，入 git）
    任务卡/<slug>.md         # 单轨 L2/L3/L4 才有
    证据/<S-ID>/             # 可选证据文件
  信号/
    轮次状态/第N轮-v{M}.json # 待处理队列（v1.2.0 起为等待的唯一真相源）
    dispatch.signal          # 一期文件式信号（历史，现由 HTTP 网关取代）
    dispatch.ack             # （历史）
    watch.ack                # 插件→仲裁者：回执到齐（历史，v1.2.0 改由状态文件表达）
    alert.signal             # 插件→仲裁者：超时/卡死告警
    ping.signal              # （历史）
    ping.ack                 # （历史）
```

**目录边界**：单轨只写 `单轨/`；多轨只写转达/回执/就绪/快照/契约块/交接手册；`信号/` 只由插件写，单轨不写信号文件。

**铁律**：回执文件的出现与 mtime 即完成信号——编排器轮询文件系统即可，原则上不读 UI 输出。

## 2. 转达单格式

每轮一个目录 `转达/第N轮/`，每轨一个独立文件 `T-X-v{M}.md`。同一轮可对同一轨多次转达（v1、v2、…），便于修订/追加而不覆盖历史。

```markdown
# T-X · 第 N 轮 · v{M} 转达

## 收尾判据（任一命中即触发收回评估；各轨一致）
- 契约块版本达到 v1.3.0
- T-A/B/C 全部通过验收
- 出现跨轨强依赖
- 总改动行数 > 1500

## 快照
- 当前契约版本：v1.2.3
- 关键文件状态：[简要列表]

## 任务（T-X 专属）
[任务边界、目标、文件领地、验收形式]

## 时序约束
- （若有依赖）T-A 完成后本轨才能开始
```

**规则**：仲裁者按轨独立写文件，各轨只读自己的 `T-X-v{M}.md`，不读别轨文件。

## 3. 回执格式

```markdown
# T-X · 第 N 轮 · v{M} 回执

- 裁决编号引用：[#A.001]
- 完成时点：2026-10-15T10:41:00+08:00
- 证据形式：[文件路径 + 行号 / 测试通过 / 截图]
- 实际改动：[文件列表]
- 待仲裁者实检：[验证清单]

## 自检
- 错误率：x%（最近 N 次工具调用 y 次失败）
- 自评健康度：良好 / 注意 / 警告
- 建议下一轮：继续 / 准备交接 / 立即交接
```

**版本对齐**：回执的 `v{M}` 必须与本次执行的转达 `T-X-v{M}.md` 一致；编排器按「轮次 + 轨 + 版本」三元组等待对应回执。

## 3.1 就绪回执格式

轨道完成启动（读完手册、契约块、快照）并确认自己处于待命状态后，**第一件事**是写 `就绪/T-X.md`，然后才进入待命。写完回执、回到待命时，也要刷新本文件。

```markdown
# T-X · 就绪

- 就绪时点：2026-10-22T14:05:00+08:00
- 已读手册：.parallel-agent/轨道启动手册.md
- 已读契约块版本：v1.2.3
- 已读快照：是
- 已读转达单：否（启动阶段不允许读任何转达单）
- 当前状态：待命
```

**规则**：
- 启动阶段绝不读 `转达/` 下任何文件——派发只能由仲裁者的第二条消息触发。
- 转达单可能在你启动之前就已落盘（仲裁者被允许提前写），**看到也不读**；「文件存在」不代表「该执行」。
- 本文件无轮次、无版本，同一轨始终只有一份，每次进入待命覆盖重写。
- 编排器只认 `mtime >= 等待起点` 的就绪文件，历史遗留文件不算数。

## 4. 契约块格式

契约块是最终结论，嵌在代码注释里，不包含推理过程：

```markdown
<!-- 契约块 v1.2.3 -->
<!-- [#A.001] 模块边界：T-A 负责前端 src/ui/，T-B 负责后端 src/api/ -->
<!-- [#A.002] 接口签名：GET /api/tasks → Task[]，POST /api/tasks → Task -->
<!-- [#A.003] 文件领地：T-A 独占 src/ui/*.tsx，T-B 独占 src/api/*.ts -->
```

裁决编号 `[#A.NNN]` 是稳定引用，回执和转达单都用它。

## 5. 快照格式

```markdown
# 快照

## 当前阶段
并行多轨（阶段 2）

## 契约版本
v1.2.3

## 各轨状态
| 轨 | 状态 | 欠账 | 上轮回执 |
|---|---|---|---|
| T-A | 运行中 | 无 | 第3轮 ✅ |
| T-B | 运行中 | 等待 T-A 接口 | 第3轮 ✅ |
| T-C | 待命 | 无 | 第2轮 ✅ |

## 收回决策（如有）
收回决策（第 5 轮后）：
- 触发判据：剩余子任务正交性（重叠 45%）+ 集成验收需求
- 剩余任务：T-A 收尾 + T-B 接入 + 全局集成测试
- 收回后由谁做：仲裁者亲做（轻量）
```

## 6. 交接手册格式

**角色**：冷启动入口——给新会话/第二任仲裁者用的，不是过程记录。

**只含结构性结论**：
- 当前阶段（奠基/并行/收尾）
- 当前契约版本
- 各轨状态（运行/待命/已销毁）
- 欠账清单（剩余任务）
- 启动方式（新会话首条消息）

**不含**：过程推理、各轨执行细节、对话历史。

**版本管理**：每版保留不覆盖，新会话读最新版。

## 7. 控制信号格式

推荐顺序：**先落盘转达单 → `/new` 开轨 → `/wait-ready` 等就绪 → `/dispatch` 派发**。转达单可以提前写，派发消息必须等就绪。

`dispatch.signal`（仲裁者→插件）：
```json
{
  "batch": 1,
  "actions": [
    { "type": "new", "轨": "T-A", "手册指针": ".parallel-agent/轨道启动手册.md" }
  ]
}
```

派发是**另一批**，必须等 `就绪/T-A.md` 出现后才发：
```json
{
  "batch": 2,
  "actions": [
    { "type": "dispatch", "轨": "T-A", "话术": "读 .parallel-agent/转达/第1轮/T-A-v1.md，执行，写 .parallel-agent/回执/第1轮/T-A-v1.md" }
  ]
}
```

**信号体只含轨号 + 轮次 + 版本号 + 文件指针 + 固定话术模板，绝不含任务内容。**

### 7.1 单轨单在途消息（禁止连发）

**同一轨在同一时刻只允许存在一条未完成的消息。** 上一条消息的完成信号未到之前，仲裁者不得向该轨发送下一条消息。

**转达单不属于消息**：写文件是数据面动作，不触发轨道行为；**派发消息才是触发器**。因此允许仲裁者提前落盘转达单（包括在 `/new` 之前就写好第 1 轮转达单），唯一硬约束是**派发消息必须等轨道就绪之后再发**。

| 已发消息 | 完成信号 | 收到后才能做 |
|---|---|---|
| 新建轨（`new_track`） | `就绪/T-X.md` 出现且 mtime 不早于发送时点 | `POST /dispatch`（转达单可提前落盘） |
| 派发轮次（`dispatch_round`） | `回执/第N轮/T-X-v{M}.md` 出现 | 实检 → 写下一版转达（可提前）→ 再派发 |
| 取消待命（`cancel_standby`） | `就绪/T-X.md` 刷新（mtime 不早于发送时点） | 认为该轨已回到待命 |

**为什么派发消息必须等就绪**：轨道从收到「读手册…待命」到写出就绪回执需要读若干文件，这段窗口期内它是「启动中」而非「待命」。此时若派发消息已到达，它会与启动流程抢占同一条会话，导致「应该待命却先执行」，后续消息要么撞上已在执行的任务，要么被判定为重复而丢弃。

**为什么提前落盘转达单是安全的**：轨道在启动期**不读** `转达/` 下任何文件（见 §3.1 与轨道 Skill），执行期也只读派发消息指定的那一个版本文件，不会主动扫描目录。文件早就在那里，不会产生任何行为；版本化命名又保证新文件不会覆盖正在读的旧版本。所以「先写转达单、再开轨、就绪后派发」是合法且更高效的顺序。

### 7.2 回执待处理队列与 ack 闭环

v1.2.0 起，等待不再由仲裁者阻塞持有，而是由插件的后台 job 维护一份**状态文件**。它是等待的唯一真相源。

**文件**：`信号/轮次状态/第N轮-v{M}.json`

```json
{
  "job": "w-7f3a",
  "轮次": 1,
  "版本": 1,
  "job状态": "running",
  "notify": "each",
  "轨道": {
    "T-A": { "状态": "done",    "回执": ".parallel-agent/回执/第1轮/T-A-v1.md", "mtime": "...", "处理": "notified", "通知于": "...", "重发次数": 0, "处理于": null },
    "T-B": { "状态": "pending", "回执": null, "mtime": null, "处理": null, "通知于": null, "重发次数": 0, "处理于": null },
    "T-C": { "状态": "timeout", "回执": null, "mtime": null, "处理": "pending", "通知于": null, "重发次数": 0, "处理于": null }
  }
}
```

**两个独立维度**：

| 字段 | 取值 | 含义 |
|---|---|---|
| `状态` | `pending` / `done` / `timeout` / `failed` | 轨道本身是否干完 |
| `处理` | `null` / `pending` / `notified` / `done` | 仲裁者的消费进度 |

`notified` 不可省：注入后到 ack 前若只记 `pending`，插件会误以为还没通知而重复注入同一回执。

**入队规则**：
- `notify="each"`（默认）：每轨回执稳定出现即 `处理=pending`
- `notify="all"`：全部轨进入终态（done/timeout/failed）时才统一置 `pending`
- `timeout` / `failed` 例外：立即置 `pending` 并使用告警话术，不等其余轨

**消费规则**：
1. 仲裁者处理完一条的**实检记录已写入快照**之后，调用 `POST /watch/ack {job, 轨}`
2. 插件把该轨 `处理=done`，并在响应里带回 `剩余待处理` 与 `未完成`
3. 剩余非空 → 仲裁者**不结束回合**，继续取下一条；为空且仍有轨未完成 → 结束回合等下次唤醒
4. ack 幂等；禁止 ack 一个 `状态=pending` 的轨

**写入权**：状态文件只由插件写。仲裁者通过 HTTP 让插件写，禁止直接编辑（避免并发写坏、避免伪造消费记录）。

**通知条件**（插件侧）：存在 `处理=pending`（或超时未 ack 的 `notified`）**且** 仲裁者空闲 **且** 输入框为空。仲裁者 busy 或有草稿时只更新状态文件，不注入。

### 7.3 多 job 并存（不同轨处于不同轮次）

现实中各轨进度不同：T-A 可能在第 1 轮，T-B 已到第 3 轮。规则：

| 项 | 规则 |
|---|---|
| 粒度 | **每「轮次 + 版本」一个 job**；跨轮必须分多次 `POST /watch` |
| 状态文件 | 按 `第N轮-v{M}.json` 独立存放，文件名唯一，互不覆盖 |
| 重复提交 | 同「轮次 + 版本」已有 **running 或 done** 的 job → 幂等复用，返回已有 `job_id`；响应 `复用=true` |
| 已完成后再提交 | job 已 `done`：纯重复 → 警告「已处理完毕」；带新轨 → 追加到该 job 并恢复 `running`，已处理轨不重复入队 |
| 缺轨（运行中） | running job 收到新轨 → `警告` 点名，需换新版本号重新提交 |
| 同轨冲突 | 同一轨挂在另一个未清账 job 上 → `警告` 点名，先处理旧 job 再派新活（单轨单在途的延伸） |
| 唤醒与消费 | 一次注入可对应一个 job，但仲裁者被唤醒后必须先 `GET /watch/jobs` 拉全量，逐 job 逐条 ack |
| 评估 | 每个 job 各自集齐就各自做整轮评估，不互相等待 |

## 8. 固定话术模板

控制面绝不传裁决内容，只用以下固定模板：

| 场景 | 话术 |
|---|---|
| 新建轨首条 | `读手册 .parallel-agent/轨道启动手册.md，你是 T-X，待命` |
| 派发轮次 | `读 .parallel-agent/转达/第{N}轮/T-X-v{M}.md，执行，写 .parallel-agent/回执/第{N}轮/T-X-v{M}.md` |
| 取消待命 | `本轮无 T-X 任务，待命` |
| 第二任仲裁者启动 | `读交接手册第 N 版 .parallel-agent/交接手册/第N版-*.md，你是仲裁者 II 世，承接 T-A/B/C 收尾` |
| 第二任分轨启动 | `读交接手册第 N 版 .parallel-agent/交接手册/第N版-*.md，你是 T-X II 世，承接 T-X 身份` |
| 回执待处理通知 | `读 .parallel-agent/信号/轮次状态/ 下的待处理状态文件（当前 job {ID}），可用 GET /watch/jobs 查看全部；处理完用 POST /watch/ack 标记` |
| 超时/失败告警 | `读 .parallel-agent/信号/轮次状态/ 下的待处理状态文件（当前 job {ID}），有轨超时或失败，优先处理；可用 GET /watch/jobs 查看全部` |

## 9. HTTP API

编排器插件监听 `127.0.0.1:9318`，仲裁者 Skill 通过 fetch 调用：

| Endpoint | 入参 | 出参 | 动作 |
|---|---|---|---|
| `POST /dispatch` | `{轨:"T-A", 轮次:1, 版本:1, 模板:"dispatch_round"}` | `{ok, sid, sent_at}` | 切轨 → 断言 → 注入话术 → 发送 |
| `POST /new` | `{轨:"T-A", 模板:"new_track"}` | `{ok, sid, named_at}` | 新建任务 → 注入首条 → 发送 → 落身份表 |
| `POST /wait-ready` | `{轨:["T-A"], since:1690000000000, timeout_s:300}` | `{ok, since, 就绪:[...], 未就绪:[...]}` | 阻塞等待 `就绪/T-X.md` 出现且 mtime ≥ since |
| `POST /watch` | `{轮次:1, 版本:1, 轨:["T-A","T-B","T-C"], timeout_s:1800, notify:"each"}` | `{ok, job_id, 状态文件, 复用, 警告:[...]}` | **提交后台 job 并立即返回**，不阻塞；同轮次版本幂等复用 |
| `GET /watch/status` | `?job=w-7f3a` | `{ok, job状态, 轨道, 待处理:[...], 未完成:[...]}` | 只读查询待处理队列 |
| `POST /watch/ack` | `{job:"w-7f3a", 轨:"T-A"}` | `{ok, 剩余待处理:[...], 未完成:[...], 全部已处理}` | 标记该轨已消费，并带回剩余队列 |
| `POST /watch/cancel` | `{job}` | `{ok}` | 取消 job，停止轮询并清理 |
| `GET /watch/jobs` | — | `{ok, jobs:[...]}` | 列出全部 job（自检与恢复） |
| `POST /bind-arbiter` | `{}` | `{ok, sid, 任务名}` | 把当前选中会话绑定为仲裁者（通知目标） |
| `GET /ping?sid=xxx` | sid | `{ok, 状态:"running"/"idle", 任务名}` | 读状态 |
| `POST /delete` | `{sid}` | `{ok}` | CDP 菜单序列删除 |
| `GET /health` | — | `{ok, cdp_alive, 轨表}` | 自检（CDP 未连时仍可访问） |

**所有 endpoint 入参不含任务内容**——只含轨号、轮次、文件指针、话术模板标识。
