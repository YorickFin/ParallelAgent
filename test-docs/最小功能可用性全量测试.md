# ParallelAgent 最小功能可用性全量测试

> **用途**：在一个**空项目**里打开 Trae，把下面「提示词正文」整段复制给 AI 执行。
> **目标**：用最少步骤覆盖 ParallelAgent 的全部功能点，回答“现在还能不能用、最小可用是否成立”。
> **测试项目**：不要选 ParallelAgent 源码仓库；所有测试产物都留在空项目里。
>
> **与《全量基础测试Prompt.md》的分工**：
>
> | 文档 | 回答的问题 | 深度 | 什么时候用 |
> |---|---|---|---|
> | `全量基础测试Prompt.md` | TRAE 更新影响了哪一层 | 依赖面取证 + 异常/回归 + 归因 | 更新后定位问题 |
> | `最小功能可用性全量测试.md` | 现在还能不能用，最小可用是否成立 | 全功能清单 + 每项只跑最小主路径 | 更新后快速验收、发布前冒烟 |
>
> **使用前替换**：
> - `<ParallelAgent仓库>` → ParallelAgent 源码仓库绝对路径（例如 `e:\备份\project\Agent\ParallelAgent`）。
> - 其余路径、版本、端口均按现场实测记录。

## 提示词正文

你是 **ParallelAgent 最小功能可用性全量测试**的执行者。当前项目是一个空项目。TRAE 刚刚更新，你要用最短路径把 ParallelAgent 的功能点逐个跑一遍，并在项目根目录写一份 `最小功能可用性测试报告.md`。

**核心原则**：每个功能点至少跑一次主路径；“最小”不等于“跳过”；不追求深度根因，只判断可用/不可用/降级。

### 0. 目标与判定口径

#### 0.1 功能点分级

| 级别 | 含义 | 对“最小可用”的影响 |
|---|---|---|
| `P0` | 主路径，缺了就不能算可用 | 任一 FAIL → 不可用 |
| `P1` | 完整功能集的重要组成，但不阻断主路径 | FAIL → 最小可用但降级 |
| `P2` | 运维、恢复、卸载等辅助能力 | 未覆盖不影响最小可用结论 |

#### 0.2 最终结论

| 现场结果 | 结论 |
|---|---|
| P0 全部 PASS，P1 全部 PASS | **最小可用** |
| P0 全部 PASS，至少一个 P1 FAIL | **最小可用（有降级）** |
| 任一 P0 FAIL | **不可用** |
| 多个 P0 BLOCKED，证据不足 | **无法判定** |

失败项只做轻量归属，不展开深度根因：

- `C`：疑似 Trae 更新兼容问题
- `P`：项目缺陷
- `E`：环境/安装问题
- `U`：未验证

### 1. 硬性规则

1. **不许编造结果**。没执行的用例标 `BLOCKED` 或 `SKIP`，写清原因。
2. **证据只认可核对内容**：命令 + 输出/退出码、文件路径、diff。
3. **不要修改 ParallelAgent 源码仓库**；只读仓库里的 CLI、Skill、reference。
4. **不要自动提交到远端**；当前项目只做本地 git 提交。
5. **涉及删除/卸载/重置/重启 IDE/开新窗口/新会话的操作，先问我**。
6. **L1 提问、L3 验收确认、L4 拆轨确认必须等我回答**，不得自问自答。
7. 每个用例结束后立即写报告；不要最后一次性补写。
8. Skill 没激活就记 `FAIL`，不要手工模拟流程凑通过。
9. 开始时用 TodoWrite 建立用例清单，逐项更新。
